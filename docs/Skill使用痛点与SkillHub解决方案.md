# Skill 使用痛点与 SkillHub 解决方案

> 文档性质：产品定位、需求说明与推广参考材料  
> 保存范围：仅本地开发使用，不同步远端  
> 更新日期：2026-09-02

## 1. 核心判断

SkillHub 不是另一个单纯的 Skill 下载器，也不是替代 Agent 运行 Skill 的平台。它解决的是：当一个用户同时使用多个 Agent、多个开发项目和大量本地 Skill 后，如何知道自己有什么、哪些地方正在使用、是否安全、是否重复、如何部署，以及发生变更后如何恢复。

一句话定位：

> SkillHub 是 Windows 和 macOS 上的本地 Skill 控制中心，以集中库为唯一管理来源，统一完成发现、理解、检查、部署、更新、回滚、备份和迁移。

需要注意：不同 Agent 对 Skill 的加载方式并不一致，不一定会把所有 Skill 正文一次性放入上下文。但可用 Skill 过多，仍可能增加候选描述、检索、工具选择和路由噪声，也会提高用户人工管理成本。SkillHub 的目标是让每个 Agent、每个项目只获得当前真正需要的 Skill。

## 2. 痛点与对应解决方案

### 2.1 Skill 太多，但真正需要的很少

| 用户痛点 | 典型后果 | SkillHub 的解决方式 | 边界 |
| --- | --- | --- | --- |
| 安装了几十甚至上百个 Skill，长期高频使用的可能不到 10 个 | 用户找不到真正有用的 Skill；Agent 的候选能力过多，选择噪声增加 | 集中库保存全部 Skill，按 Agent、项目和用途选择性部署，不要求所有 Skill 全局启用 | SkillHub 负责管理文件和关系，不承诺 Agent 一定调用正确 |
| 不同 Agent 用途不同，却共用同一批全局 Skill | 编程、办公、研究等场景互相干扰 | 分别管理每个 Agent 的全局 Skill；支持单选、多选 Agent 部署和解除部署 | Agent 是否支持全局或项目级目录，以适配资料和实际文件能力为准 |
| 项目需要的 Skill 组合不同 | 每次开项目都要手动复制和清理 | 项目工作台、项目标签、保存筛选视图，以及按项目批量部署或解除部署 | 不移动或重命名用户真实项目目录 |
| 很久没用的全局 Skill 长期堆积 | 全局目录越来越乱，用户不知道该删哪些 | 提供 Agent 全局 Skill 使用证据分析，按时间范围和阈值给出移出全局的参考建议 | 实验功能；只使用可获得的本地证据，证据可能不完整；关联 Runtime Hook 项目仍在研发中 |
| 临时试用的 Skill 容易忘记处理 | 试用内容最后变成永久堆积 | 使用“临时试用”标签和待处理提醒，提供转正、延长复核或删除入口 | 不创建第二套试用库，不代表隔离或安全认证 |

### 2.2 文件分散，平台规则不统一

| 用户痛点 | 典型后果 | SkillHub 的解决方式 | 边界 |
| --- | --- | --- | --- |
| 各 Agent 的用户级、项目级 Skill 目录不同 | 用户必须了解 Codex、Claude、Cursor 等平台各自的目录规则 | 内置 Agent 适配档案，识别已知目录，并允许用户添加自定义 Agent 和自定义 Skill 目录 | 只识别客户端和文件目录，不通过版本号推断 Skill 一定可用 |
| Skill 本质上散落在许多文件夹中 | 删除、升级和查找都要逐个目录操作 | 初始化时扫描已知 Agent、项目和通用目录，统一展示发现结果和来源 | 无法访问的目录明确显示，不能假装已扫描完整机器 |
| 同一 Skill 被复制到多个 Agent 和项目 | 重复占用空间；某一份修改后，其他副本逐渐不一致 | 使用本地集中库作为管理源，优先从集中库向 Agent 或项目创建符号链接；不支持链接时使用受管复制兜底 | Windows 权限、Agent 支持情况和文件系统能力不同，不能承诺所有目标都使用链接 |
| 用户导入本地 Skill 后担心多出一份副本 | 原目录和集中库同时存在，看起来重复 | 对已位于识别目录中的 Skill，建立来源和部署关系；导入时明确复制、移动或纳管方式，不静默改变用户原文件 | 默认保护用户原文件；移动等破坏性操作必须明确确认 |
| `~/.agents/skills` 并非所有 Agent 的统一标准 | 错误共享会造成部分 Agent 看不到 Skill | “共享给兼容 Agent”仍从集中库分别部署到各 Agent 自己的真实目录，不把 `.agents/skills` 当作全平台标准 | 用户可手动选择目标 Agent，支持单选和多选 |
| 普通用户不懂 Git、命令行或 `npx` | 难以安装来源仓库中的 Skill，也不清楚命令是否安全 | 提供图形化导入；识别本地目录、压缩包、Skill 页面链接、仓库链接和受支持的命令描述 | 对 `npx` 等命令优先解析来源而不是直接执行；不要求用户安装 Git |

### 2.3 看不懂、分不清、搜不到

| 用户痛点 | 典型后果 | SkillHub 的解决方式 | 边界 |
| --- | --- | --- | --- |
| Skill 有中文、英文和缩写，仅凭文件夹名难以判断用途 | 用户不敢删，也不知道该部署哪个 | 支持显示别名、标签和“我的用途说明/备注”，并让这些信息参与搜索 | 用户信息保存在 SkillHub 管理数据中，不擅自改写原始 `SKILL.md` |
| 英文描述阅读成本高 | 普通用户浏览和比较困难 | 可调用已配置的 LLM 翻译描述，保存为视图层译文，并保留原文切换 | 翻译失败时显示原文；译文不覆盖原始内容 |
| 同名 Skill 可能来自不同来源、内容完全不同 | 导入时覆盖旧文件，或者用户误删更合适的版本 | 集中库使用内部唯一身份保存同名 Skill；根据名称、来源、哈希、结构和内容检查完全重复与同名冲突 | 部署到同一目标目录时仍需解决运行时名称冲突，界面别名不能绕过它 |
| 不同名称的 Skill 可能功能重复或存在包含关系 | 同类 Skill 越装越多，选择困难 | 先用确定性规则、FTS5 全文检索和 BM25 筛选候选，再可选使用 LLM 比较共同能力、独有能力和包含关系，并给出保留建议 | 不引入向量模型；LLM 只给建议，不自动删除、合并或修改 Skill |
| Skill 多以后难以快速定位 | 只能靠文件资源管理器逐个打开 | 按名称、别名、说明、备注、标签、来源、Agent、项目、状态和部署关系搜索筛选；支持保存筛选视图 | 默认面向个人本地规模设计，性能基准以不超过约 300 个 Skill 为主 |
| `SKILL.md` 包含代码块、表格和其他 Markdown 格式 | 系统没有 Markdown 软件时无法方便阅读 | 内置安全 Markdown 阅读视图、源码视图和轻量编辑器，支持常见 Markdown 内容 | Markdown 中的代码、HTML 或图表内容不得在应用中任意执行 |
| Skill 声明了 Python、ffmpeg、MCP、插件或环境变量，但用户不知道 | 部署后才发现缺少运行条件 | 展示作者明确声明的要求，并用固定规则标出依赖文件、命令和环境变量引用线索 | 不使用 LLM 猜测依赖，不自动安装依赖，也不判断 Agent 一定能够运行 |

### 2.4 安全、重复和删除风险难以判断

| 用户痛点 | 典型后果 | SkillHub 的解决方式 | 边界 |
| --- | --- | --- | --- |
| 从互联网下载的 Skill 可能包含危险命令、敏感信息或供应链风险 | 用户可能在不了解内容的情况下交给 Agent 执行 | 导入前自动执行确定性的基础安全检查，覆盖危险命令、敏感信息、远程下载执行、路径逃逸等可确认模式 | 基础检查不执行 Skill，不等于安全认证 |
| 固定规则无法理解多文件组合、隐含意图和提示词注入 | 单纯关键词检查容易漏掉语义风险 | 提供独立、可选的 LLM 安全检查，补充提示词注入、权限诱导、数据外传、规避表达和多文件组合风险 | LLM 结果单独展示；不配置 LLM 时不影响基础管理和基础检查 |
| 用户在 Skill 中填写自己的 API Key | 安全检查可能误把合法配置当成必须删除的内容 | 允许用户保留；识别后提示风险并默认遮盖，在备份、导出、共享或发送云端 LLM 前再次确认 | SkillHub 不静默删除或改写用户 Key；SkillHub 自己管理的凭证进入系统安全凭据存储 |
| 删除 Skill 时不知道哪些 Agent、项目或组合仍在使用 | 删除集中库后造成多个部署同时失效 | 删除前生成影响清单，并提供解除选定部署、解除全部部署、保留独立副本、替换引用、归档或取消等明确选项 | 执行前重新扫描关系，不能只依赖旧的检查结果 |
| 目标目录中存在用户文件、Agent 内置 Skill 或外部修改 | 一键删除可能误删非 SkillHub 管理的数据 | 区分集中库对象、受管部署、用户原文件、内置内容和未知文件；仅删除确认归 SkillHub 管理的目标 | 发现未知文件或共享物理目标时禁止静默删除整个目录 |
| 批量导入或部署过程中部分成功、部分失败 | 用户不知道哪些已完成，也难以重试 | 使用结构化操作进度和逐项结果，失败项可重试或恢复，并汇总到待处理事项 | 不用一个模糊的“失败”覆盖全部对象 |

### 2.5 版本、外部变化和长期维护缺少闭环

| 用户痛点 | 典型后果 | SkillHub 的解决方式 | 边界 |
| --- | --- | --- | --- |
| Skill 来源更新、本地又做过修改 | 升级时容易覆盖个人调整 | 保存来源和内容身份，更新前比较差异；存在本地修改时阻止静默升级并要求用户决定 | 不使用 LLM 自动合并有冲突的内容 |
| 修改 `SKILL.md` 后想恢复旧内容 | 手工修改不可追踪，改坏后难以恢复 | 轻量编辑保存时创建新版本，支持版本比较、切换和回滚 | 内容回滚不同时回滚标签、备注、部署关系等管理数据 |
| Agent 或项目中的受管副本被外部修改 | 集中库与实际使用内容不一致 | 检测外部变化，提供比较、收集为新版本、从集中库恢复、保留独立副本或忽略 | 不把外部修改静默传播到其他 Agent 或项目 |
| 自动升级过于激进，手动升级又容易忘 | 要么长期过期，要么更新后破坏项目 | 自动检查和自动升级分开设置；支持全局、批量和单 Skill 策略，项目固定版本优先；升级前建立恢复点 | 默认自动检查并通知，不自动升级；风险、冲突、来源变化和项目固定会阻止自动升级 |
| 重新安装系统或更换 Windows/macOS 设备后难以迁移 | Skill、备注、版本和项目关系丢失 | 完整备份、恢复和换机迁移；备份包含内容、版本和可迁移管理信息，并带清单与校验值 | API Key、本机绝对路径和系统安全凭据不进入标准备份，需要在新设备重新配置 |
| NAS、SMB、iCloud、OneDrive、百度云盘等位置看起来都能放集中库 | 并发、离线和同步冲突可能破坏数据 | 设置页预留“网络存储模式”入口和迁移方向 | 下一大版本规划，本版本不宣称已支持网络存储、云盘同步或冲突合并 |
| 来源失效、目录迁移或集中库暂时不可访问 | 链接断开，自动写入可能扩大问题 | 集中库健康检查、重新定位和关系修复；不可访问时暂停相关写操作 | 不把网络暂时断开误判为内容应被删除 |

### 2.6 管理过程缺少整体视图

| 用户痛点 | 典型后果 | SkillHub 的解决方式 | 边界 |
| --- | --- | --- | --- |
| 用户不知道本机到底有多少 Skill、部署到了哪里 | 文件存在，但关系不可见 | 首页展示 Skill 数量、Agent/项目覆盖、部署关系和待处理摘要；技能库提供高密度管理视图 | 最近操作属于日志，不作为首页核心内容 |
| 多个项目数量远多于 Agent，难以分类 | 复杂目录树反而改变真实项目结构 | 项目支持收藏、多标签和保存筛选视图，一个项目可属于多个分类 | 标签仅用于 SkillHub 内部整理，不创建多层文件夹树 |
| 各类问题散落在不同页面 | 用户忘记处理试用、冲突、升级阻断或备份失败 | 待处理中心统一汇总安全发现、重复冲突、外部变化、升级阻断、试用复核和失败操作，并提供直接处理入口 | 待处理事项必须链接到确定的问题和操作，避免只有提示没有闭环 |
| 普通用户首次打开软件不知道从哪里开始 | 看见空页面，不理解集中库、扫描和部署概念 | 分步初始化向导：选择或创建集中库、扫描 Agent 和 Skill、确认兼容项、导入并完成首次部署；非必要步骤可跳过 | 集中库是使用基础；v0.2.0 正在补齐首次启动的生产闭环 |

## 3. 从“功能集合”提炼出的产品价值

### 3.1 少而准确

不要求把所有 Skill 塞给所有 Agent，而是让用户为不同 Agent 和项目选择真正需要的少量能力，减少管理成本和候选噪声。

### 3.2 一份内容，多处使用

集中库保存受管内容，Agent 和项目只建立部署关系。优先使用链接，必要时使用受管复制，减少重复占用和版本漂移。

### 3.3 看得懂，分得清

别名、用途说明、备注、标签、描述翻译、全文搜索和重复分析共同解决“名字看不懂、功能分不清、装了找不到”的问题。

### 3.4 每次高风险操作都有影响预览

导入前检查，升级前比较，删除前列出依赖，外部修改后让用户选择。SkillHub 的重点不是替用户武断决定，而是把文件关系和风险变得可见、可处理、可恢复。

### 3.5 从发现到退出的完整闭环

发现、导入、试用、部署、检查、更新、编辑、版本、回滚、解除部署、归档、删除、备份和迁移都围绕同一 Skill 身份和操作历史组织，避免每一步都回到文件资源管理器手工处理。

## 4. 明确不应夸大的边界

- SkillHub 管理的是文件、元数据和部署关系，不负责保证 Agent 一定加载、调用或正确执行某个 Skill。
- “检查通过”表示当前规则或当前一次 LLM 检查没有待处理发现，不代表经过安全认证。
- LLM 完全可选；核心本地管理、基础检查、搜索和确定性重复检查不依赖 LLM。
- 使用证据分析是实验功能，不能把证据缺失显示成“调用次数为零”。
- SkillHub 不自动安装 Python、ffmpeg、MCP、插件等 Skill 运行依赖。
- 网络存储和云盘同步是下一大版本方向，当前只预留说明和入口。
- 当前公开的 v0.1.0 应定位为早期技术预览；v0.2.0 的重点是补齐首次使用、生产数据接入和核心流程闭环后，再按产品完成度发布。

## 5. 对外传播时可使用的简短表述

> 多个 Agent、多个项目、几十上百个 Skill，不该靠你在一堆隐藏文件夹里反复复制和删除。SkillHub 把本地 Skill 集中起来：看得懂、查得清、按需部署、更新可回滚、删除前知道影响。每个 Agent 只使用真正需要的 Skill，其余内容仍由你统一掌控。
