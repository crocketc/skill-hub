# SkillHub 架构深化实施方案（2026-09-12）

> **文档定位**：本文是下一阶段"优化架构"开发任务的唯一总输入。它完整覆盖 2026-09-12 架构审查发现的 7 项候选，给出目标、流程、规范、编排与验收标准。**本文只做规划，不伴随任何代码变更**；实施启动时按第 5 章规范执行，完成后按 AGENTS.md 义务同步四份当前文档。
>
> **证据基线**：git 热点统计（最近 300/819 提交）+ Rust 后端 / React 前端 / 测试面三路并行走查 + 孤儿服务逐个核对（后台代理已完成）。承重数字均经抽查核实。本文取代同日生成的临时 HTML 审查报告（临时目录产物，已过期不入库），并修正其两处口径（见附录 B）。
>
> **阅读顺序**：第 1 章定方向 → 第 4 章看排期 → 第 3 章逐项查方案 → 第 5 章是实施时的行为准则。

## 1. 目标与非目标

### 1.1 背景

SkillHub v0.2.0 功能面已闭环，自动化证据充分（1,186 条前端测试 + 363 条 e2e + Rust 全仓测试通过）。但审查显示复杂度正在向少数几个文件集中，未来的功能开发会越来越贵：

| 热点 | 规模 | 变更频率（最近 300 提交） |
|---|---|---|
| `crates/skillhub-application/src/lib.rs` | 7,717 行 · 265 个函数 | 96 次（全仓 819 提交的 11.7%） |
| `apps/desktop/src/i18n/*/common.json` ×2 | 各 2,300 行 | 137 / 136 次（锁步编辑） |
| `apps/desktop/src/api/bindings.ts`（生成物） | 2,382 行 | 76 次 |
| 前端 14 对 `api.ts`/`nativeApi.ts` | 共 5,676 行 | 与 features 同步增长 |
| `crates/skillhub-application/tests/facade.rs` | 5,427 行 | 64 次 |

### 1.2 目标

深化（deepening）：把**浅模块**（interface 复杂度 ≈ implementation 复杂度）变成**深模块**（interface 小、implementation 吸收复杂度）。评价维度只有两个：

1. **可测试性**：每个关注点能通过一个稳定的 interface 单独测试；错误路径不需要手搭现场就能触发。
2. **AI 可导航性 / 人的可导航性**：理解一个概念不需要在多个文件间跳转（locality）；新增一个功能要改的地方数量可数且有单一入口（leverage）。

### 1.3 非目标（明确不做）

- **不改用户可见行为**：命令/查询结果、错误文案、操作日志表内容、UI 文字全部冻结。候选允许"内部接缝迁移"，但必须携带等价性证据（见 5.1）。
- 不新增产品功能，不顺手升级依赖，不迁移 DB schema（7 项候选均不需要）。
- 不引入新框架级抽象（不做 DDD/CQRS 式大重构；不引入状态管理库）。
- **不直接修改 `main`**：每场战役独立分支 + 独立 worktree（AGENTS.md 规则）。
- 不追求"一次做完 7 项"：按第 4 章三场战役推进，每场战役结束都是可发布、可停止的状态。

## 2. 词汇与决策记录机制

### 2.1 架构词汇（实施全程统一用语，启动时落入 `CONTEXT.md`）

| 术语 | 含义 |
|---|---|
| module（模块） | 一个有名字的代码归属单元，有自己的 interface 和 implementation |
| interface | 别人能用它的全部表面；**interface 即测试面** |
| implementation | interface 背后的全部细节 |
| depth / deep / shallow | 深模块：interface 小、implementation 承担复杂度；浅模块：interface 几乎和 implementation 一样宽 |
| seam（接缝） | 两个模块之间可替换的交界；**一个 adapter = 假想接缝，两个 adapter = 真实接缝** |
| adapter（适配器） | seam 的一个具体实现（生产的与测试的各算一个） |
| leverage | 一处定义、N 处受益的放大效应 |
| locality | 相关逻辑在空间上集中；bug 集中在一个模块里 |
| deletion test（删除测试） | 删掉疑似浅模块：复杂度会"集中"（说明它没干活，删）还是只是"挪个位置"（说明它承载了什么）？ |

### 2.2 领域词汇种子（启动时与 2.1 一起写入 `CONTEXT.md`）

集中库、Skill、部署关系（复制/链接）、解除部署、来源（verified_upstream / local_only / search_candidate 三分）、搜索候选、发现（本机/在线）、导入向导、组合、忽略规则、操作日志、确定性安全检查（与 LLM 增强的边界）、四种移除对象、版本与恢复。深模块命名时优先使用这些词（如"操作日志切面"而非"journal helper 集合"）。

### 2.3 决策记录（ADR）

启动时创建 `docs/adr/`。凡出现"否决 + 承重理由"或"选型 + 被放弃的替代方案"，写编号 ADR，避免未来审查重复提出同样的问题。本方案预置 5 个待写 ADR，见 7.2。

## 3. 七项候选（逐项：证据 → 问题 → 方案 → 收益 → 风险 → 验收）

> 强度含义：**Strong** = 证据充分、收益明确、建议必做；**Worth exploring** = 真实摩擦、方案需一次选型；**Speculative** = 单独做收益存疑，需绑定其他候选。

### 3.1 候选 1 · 拆解门面 God module【Strong｜ports & adapters】

**证据**
- `lib.rs` 内部结构（按行号）：结构体 `LocalApplicationFacade`（86–116，27 个字段含 6 个 Mutex 状态表：`prepared_imports`、`prepared_uninstall`、`path_grants`、`assembly_plans`、`llm_runs`、`upstream_origins`）；`LocalDeploymentBackend`（125–698，约 570 行，实现 core 的 3 个 Backend trait，却住在门面文件里）；固有 impl 块（698–4557，3,859 行覆盖 ≥12 个关注点）；execute/query 分发 match（4557–5306）；更多 impl（5306–6374）；`DeletionImpactMatrix`（6374–6606）；本地端口适配器（6606–7164）；内联测试（7164 起）。
- 49 处重复的 Mutex 锁错误 stanza（`RecoveryAction::Retry` 计数）。
- 分发 match 已开始腐烂：多数臂是一行委托，但 `SetDesktopPreferences`（4560–4569，含网络闸门副作用）、`CommitRepair`/`ResolveRecovery`（4639–4666，手拼 OperationSummary）、`GetBootstrapSnapshot`（5033 起，约 25 行）内嵌真实逻辑。

**孤儿服务判定表（2026-09-12 逐个核对，实施时按此执行）**

`crates/skillhub-core/src/application/` 共 21 个模块，其中 **10 个已在生产使用**（CallPolicy、Deployment、Duplicate、Health、Ignore、Reconcile、Recovery、Removal、SearchQuery、Translation，`lib.rs:39-45` 引入）——证明"port trait + 泛型服务"是本仓库已验证的模式。问题只在 8 个零引用文件 + 1 个半接线文件：

| 服务 | 行数 | 判定 | 理由（一句） |
|---|---|---|---|
| `CheckService` | 207 | **吸收** | 与门面 `execute_basic_check`（3177–3241）相似度最高：同一 run_id 方案、同 generation 递增、高风险处置门逐行一致；走 Scanner/Materializer port 即可接纳 |
| `ProjectAssemblyService` | 311 | **吸收（收尾）** | 已被门面包装调用（`LocalAssemblyService` 6623–6653）；唯一残余：计划表存在门面 `assembly_plans` Mutex（112）与服务私有 map 两处，需归一 |
| `ImportService` | 163 | **吸收·重写** | prepare/commit/cancel 框架一致；门面超集（origin/upstream 记录、描述解析、补偿），服务独有决策（EstablishManagedRelation/TakeOverAfterVerify）门面反而不支持——需对齐决策集（见 7.1 开放问题 2） |
| `CatalogService` | 349 | **吸收·重写** | capture→insert→set_current→portable 骨架与 `create_skill_flow`（3514–3596）镜像；port 需再吸收 4 步（materialize、relink、set_revision、record_version） |
| `LlmSafetyService` | 115 | **吸收·重写** | 同一 `llm-safety-{version}-{gen}` 血统；门面超集（证据组装、凭据掩码、单飞注册表 `llm_runs`）需反哺服务契约 |
| `SourceService` | 73 | **吸收·重写** | KeepLocal/Cancel 早退与"上游更新会覆盖本地修改"守卫一致；门面是 Git 专用管线（AR-017/020/021），port 形状可抽象它但服务体太薄 |
| `OperationService` | 677 | **收编（大幅缩减）** | saga 语义（幂等重放、写者许可、undo）超出产品现状——门面只写"被动历史"；同表同阶段存储兼容（`storage/tests/operation_repository.rs` 证明双实例共享一库）。采用方向：保留 journal 存储 + 候选 2 的切面；saga/undo 部分删除（ADR-0002） |
| `WatchService` | 462 | **删除** | 全工作区无任何 WatchHint 生产者；门面注释（~3764）明确外部变化由 health/reconcile 负责。纯思辨代码 |
| `VersionService` | 122 | **删除** | 纯委托层；门面经 `library_runtime.snapshot()` 直连仓储，唯一真逻辑（set_current 回滚）在门面里 |

> **决策状态（2026-09-12，已确认）**：上表及第三档立场（OperationService 不整体吸收 saga，只保留 journal 存储与仓储、删除 undo/重放残余；ImportService 先按门面现有决策集吸收，"接管"类决策留作开放问题 2）已经项目负责人确认，执行时不再重新论证。若实施中发现与本表冲突的事实，按 ADR 机制修订并更新本表，不得静默偏离。

**问题**：interface 只有 2 个方法（`execute`/`query`），实现却把 12+ 个关注点、6 份可变状态焊在一个文件；同一批流程与 core 服务双份存在（生产跑门面副本，服务副本零引用）。locality 最差形态。

**方案**（方向：延续已验证的 core::application 服务模式，而不是另起炉灶）
1. 候选 2 的切面先行（3.2）。
2. `LocalDeploymentBackend`（125–698）搬入 `skillhub-adapters`（与 GixSourceFetcher 等作伴）；seam 不动，实现归位。
3. 按判定表逐个吸收：门面内联流程移入对应 core::application 服务（先补 port，再搬流程，每次一个服务独立提交序列）。
4. 删除 WatchService、VersionService、OperationService 的 saga 残余；按 5.3 规则移植有价值的测试。
5. 分发 match 瘦身：内嵌逻辑（SetDesktopPreferences 等 3 处）下沉为方法，match 恢复纯路由。
6. `DeletionImpactMatrix`（6374–6606）归位到删除/解除部署语义的归属模块（实施时定名，写入 CONTEXT.md）。
7. 构造变体收敛由候选 6 承接（3.6）。

**收益**：locality——每个流程一个有名字的归属；leverage——"port trait + 泛型服务"模式从 10 个服务推广到全部流程；删除 ~2,200 行死实现与 49 处重复 stanza；热点文件的每次变更从"全文件冲突风险"降为"单模块变更"。

**风险与缓解**：热文件合并冲突（短命分支、小步合入）；Mutex 状态隐性耦合（每份状态随流程走，如 `prepared_imports` 随导入流程进服务）；行为漂移（先表征测试后搬家，见 5.2）。

**验收**
- [ ] `lib.rs` ≤ 1,500 行（只剩：结构体、状态、分发 match、装配）；
- [ ] 8 个零引用文件按判定表清零（吸收 5 + 删除 2 + 收编 1）；
- [ ] 分发 match 无内嵌逻辑臂；`*_for_tests` 与构造变体清零（与候选 6 合并验收）；
- [ ] 全部既有契约测试保持绿色，未删除任何断言。

### 3.2 候选 2 · 操作日志 `journaled()` 切面【Strong｜in-process】

**证据**：helpers 在 `lib.rs:1785-1852`，策略（prepared-known → NeedsRecovery）只存在于散文注释（1771–1782）；18 处 `journal_begin` + 17 处 `journal_settle` + 20 处 `journal_advance`（共 58 处调用点）；`commit_import` 3 路阶段探测（5615–5646）、`commit_deployment` 4 路 match（5430–5465）各不相同；提交 `2c92e40` 一次 +591 行纯接线。

**问题**：恢复语义是承重策略，却要求每个 mutation handler 手工复述 3~4 处，靠人记。

**方案**：一个包装函数 `journaled(kind, op_id, || flow())`，把 begin/settle/advance、阶段探测策略、错误白名单编码一次；阶段差异（3 路/4 路）收敛为一个小的策略参数。存储面不动：同一 `operations` 表、同一 OperationRecord/阶段词汇（存储兼容性已被 storage 测试证明）。

**收益**：leverage——一处策略 58 处受益；新 mutation 从"记得 4 个调用点"降为"套一层 wrapper"；策略从注释升为 interface；切面单独可测。

**风险**：各 handler 阶段语义有细微差异（导入探 prepared 表、部署 4 路区分）——迁移前逐个对照，先补表征测试锁住现有落库内容再动手。

**验收**
- [ ] wrapper 之外 `journal_*` 直接调用点 = 0；
- [ ] `operations` 表内容与迁移前逐字段一致（查询路径测试不变绿转红）；
- [ ] 新增一个 mutation 的日志成本 = 1 处声明。

### 3.3 候选 3 · 前端 native facade kit【Strong｜ports & adapters】

**证据**：14 对 `api.ts`/`nativeApi.ts` 共 5,676 行；非测试代码 150 处相同的 `result.type !== ...` 守卫（skill-detail 24、discovery 16、skills 14、backup 13、settings 11…）；14 个仪式性 `unavailableXxxFacade` stub（`pending/api.ts:45`、`import/api.ts:187`、`settings/api.ts:92`…）；同一 IPC 形状 4 种错误习语（`SkillLibraryUnavailableError`、`SkillDetailUnavailableError`、`ImportUnavailableError`+`ImportCancelledError`、discovery 裸 `Error`）；`describe` 包装复制 13 处（`pending/PendingPage.tsx:49-50` 等）；约定自身不一致（discovery 合并单文件、removal 的 stub 放错文件、recovery 是 3 行别名）。新查询要穿 5 层：bindings → api.ts 接口 → nativeApi 守卫 → 组件 state/effect → DataState + i18n ×2。

**问题**：同一约定手工复制 14 份，interface（守卫/stub/错误习语）几乎与 implementation 等宽——教科书式浅模块。

**方案**：建一个共享深模块（建议 `apps/desktop/src/api/native-kit/`），包含：
- `expectResult(result, type)`：统一类型守卫，替换 150 处；
- `NativeContractUnavailableError`：统一 unavailable 语义（`ImportCancelledError` 等真实特例作为类型化变体保留）；
- `useFacadeQuery` + query-key 工厂：统一数据拉取（react-query 已在 8 个文件使用，此处收编为唯一新路径）；
- `useNativeErrorText(genericKey)`：收编 13 处 describe 包装。

**与性能轮决策的衔接**：2026-09-12 性能轮曾决定"不迁移既有手动 useEffect 拉取到 react-query"——那是为避免性能修复混入实现重构。本候选就是那个被推迟的重构，由本方案承接，按 feature 渐进迁移，不搞一刀切；性能轮成果（入口 gzip ~310 kB、路由懒加载、manualChunks）作为不可回退基线。

**迁移规范**：新代码必须走 kit；热 feature（skills、skill-detail、discovery、import）按序迁移；冷 feature 顺路迁移；每 feature 一个独立提交。feature 的 `api.ts` 只留两类东西：视图模型类型、默认值/契约 interface（`skills/api.ts` 的冻结默认值等承重内容保留）。

**收益**：locality——IPC 语义一处可测；leverage——1 个 kit 服务 14+ 个 feature；新查询 5 层 → 3 行；删除 14 个 stub、4 种错误习语归 1。

**风险**：逐 feature 迁移周期长、中途新旧并存（用"新代码强制 kit"的提交纪律控制）；隐藏的每 feature 语义（取消、冻结默认值）需在迁移时显式建模。

**验收**
- [ ] kit 之外 `type !==` 守卫 = 0；unavailable stub = 1（kit 内）；错误习语 = 1；
- [ ] 新增一个查询的端到端改动 = api.ts 类型 + 3 行组件声明；
- [ ] 1,186 条前端测试全程绿色；`pnpm build:frontend` 入口 gzip ≤ 310 kB 基线。

### 3.4 候选 4 · 错误码 → 文案单一来源【Worth exploring｜ports & adapters】

**证据**：Rust 侧 `ErrorCode`（`core/src/error.rs:9+`）specta 类型化、干净；TS 侧 `api/nativeErrors.ts:85-140` 手抄约 50 个点分码字面量（`keyedMessage`），并按 `params.reason`（自由字符串，**specta 完全不可见**）分派（`operation.conflict` × 6 种 reason）；每新增一个错误码要同步 5 处：`error.rs`、`nativeErrors.ts`、i18n ×2、`i18n.test.ts` 的 20 条手维护"必需错误键"清单，且无任何跨 seam 校验；`import/nativeApi.ts:150-176` 重新实现了一份映射 + 自有 fallback；`discovery/api.ts:251-254` 因 `keyedMessage` 缺映射不得不在 `describeNativeError` 之前拦截。Rust 侧另有 49 处重复的 Retry 错误构造 stanza。

**问题**：跨 seam 契约靠手抄维持；reason 维度游离在类型系统之外。

**方案（选型已定，理由入 ADR-0003）**：**codegen 路线**——错误码枚举与 reason 收进 Rust 枚举，绑定生成时（`cargo test -p skillhub-desktop generate_bindings`，既有管线）一并生成 code→默认 i18n key 的映射与类型化 reason 联合；`keyedMessage` 手抄表改为消费生成物；"必需错误键"清单替换为生成校验测试（每个码在 zh-CN/en-US 都有键，缺键即测试红）。被放弃的替代方案：在 `AppError` 上直接携带 i18n key（有 `OperationSummary.message_code` 先例）——否决理由：把展示层关注永久焊进后端数据契约，且解决不了 reason 无类型问题。

**收益**：新错误码 5 处编辑 → 2 处（error.rs + i18n）；漏配从线上裸码变成编译/测试期错误；reason 从字符串变 interface。

**风险**：现存 reason 字符串需先盘点枚举化（可能暴露未记录的 reason 值）；未知码兜底行为（`importWorkflow.errors.unknown`）必须原样保留。

**验收**
- [ ] `nativeErrors.ts` 手写码字面量 = 0；`i18n.test.ts` 手维护清单删除，由生成校验替代；
- [ ] 新增错误码实测只改 2 处；既有错误文案 e2e 全部不变。

### 3.5 候选 5 · 类型化 fake backend 单一来源【Worth exploring｜mock】

**证据**：同一 Rust 契约存在 4 份无类型手工仿本：① e2e 无类型 IPC 假桥（`tests/e2e/native-flow-preview.spec.ts:8-216`，约 200 行 `if/else` + `args: any` + 手写 snake_case 字面量 + `__combinationCommands` 命令断言侧信道，注释自认需"逐字段对齐"）；② `features/*/testFixtures.ts` ×3（333+480+268 行）；③ `features/*/nativeApi.test.ts` 的 `vi.mock(bindings)` 字面量；④ `/__preview` 页面内联 mock facade + 40 行 `DiscoverySnapshot` 字面量（含 `import/api.ts:291-375` 生产文件里的 85 行 mock）。已发生 3 起 spec 过时事故（`5499221`、`f6e356a` 修复的 native-flow/llm-loops）。

**问题**：契约一变，4 份仿本各自在**运行期**碎裂。

**方案**：扩展 Specta 绑定生成，一并产出类型化 `fakeNativeApi`：默认填充的 DTO builder（测试只覆写关心的字段）、可注入延迟/故障、调用记录（替代 `__combinationCommands` 侧信道）。消费方逐个迁移：nativeApi 测试 → 组件测试 fixtures → `/__preview` → e2e 假桥。配套纪律：CI 加一条 grep 检查，禁止生成物之外的手写 DTO 字面量。

**收益**：4 份 DTO 知识 → 1 份生成物；locality——契约变更在一处编译期暴露；"spec 过时"事故类别消灭；e2e/preview/组件测试同源。

**风险**：生成器复杂度（serde 默认值、snake_case 映射——bindings 已解决同等问题）；e2e 假桥迁移是四步中最大的一步，单独成提交。

**验收**
- [ ] 契约变更实测只动 1 个生成文件，消费者由编译错误指路；
- [ ] 4 类消费者全部迁移；手写字面量 grep 检查进 CI；
- [ ] 363 条 e2e 全绿，运行时长不劣化（基线 ~2.8 min）。

### 3.6 候选 6 · Facade 构造注入 + testkit 采用【Worth exploring｜in-process】

**证据**：约 12 个构造变体（`lib.rs:1381-1756`：`new_with_today`、`new_with_providers_and_update_key`、`new_with_library_and_targets`、`new_with_library_and_llm_runner_and_evidence`…）；`#[doc(hidden)]` 逃逸口家族：`set_repo_discovery_provider_for_tests`（1616）、`skill_source_for_tests`（1625，`f0a5b53` 退役 IPC 查询后为行为测试保留的观测点）、adapters 侧 `with_download_base_for_tests` ×3（`github_releases.rs:52`、`repo_discovery.rs:71`、`app_update/download.rs:69`）。根因：provider 在 `new()` 内部构造，测试只能事后打补丁。`skillhub-testkit`（336 行：TempWorkspace 228 + FaultInjector 103）仅 2 个消费者；5,427 行的 `tests/facade.rs` 反而用裸 tempfile 手搭现场，故障注入不可达。

**问题**：构造接缝缺失导致测试逃逸口经济；能打故障的 testkit 够不着最需要它的测试。

**方案**：
1. `FacadeBuilder`：`repo_discovery(p)`、`opener(o)`、`installer(i)`、`clock(c)`、凭据后端等从构造器注入；生产装配一处（src-tauri），测试装配一处（testkit 扩展）。
2. 删除 `*_for_tests` 家族：adapters 的 `with_*_for_tests` 改为构造参数；`skill_source_for_tests` 的观测需求随候选 1 的流程下沉消解（来源语义测试移到归属模块，模块内测试可见内部；facade 层只留公开契约）。
3. facade 测试改用 `TempWorkspace`（替换裸 tempfile）+ `FaultInjector`（错误路径经公开 interface 触发）。
4. `tests/facade.rs` 按新模块边界拆分（每模块一个测试文件）， arrange 复用 testkit。

**收益**：`*_for_tests` 清零；错误路径不再需要手搭现场；构造变体 12 → 1；测试 arrange 缩短。

**风险**：一次性改所有测试的构造调用（先用 shim 构造函数过渡，分批切换）。

**验收**
- [ ] `grep -r "_for_tests" crates/ | grep -v testkit` = 0；构造变体 = 1（+`new(db)` 便捷入口）；
- [ ] `doc(hidden)` API = 0；FaultInjector 被 ≥ 导入/部署错误路径测试使用；
- [ ] 全部契约测试绿色，无断言降级。

### 3.7 候选 7 · i18n 命名空间拆分【Speculative → 绑定候选 4 后 Worth exploring】

**证据**：`zh-CN/common.json` 与 `en-US/common.json` 各 2,300 行、单一 `common` 命名空间、31 个顶层键混装通用词与 feature 词；300 提交中 **137/136 次锁步编辑**；`keyedMessage` 反向耦合每个 feature 的键布局（伸进 `settings.llm.*`、`deployment.results.failure.*`、`importWorkflow.errors.*`）；import 的键分裂在 `"import"`（8 处使用）与 `"importWorkflow"`（104 处使用）两处。

**问题**：每次文案变更都是 2 文件锁步提交；错误映射模块依赖全部 feature 的键布局。

**方案**：按 feature 拆命名空间（`i18n/<locale>/<feature>.json`，通用词留 `common`）；**errors 命名空间由候选 4 的生成映射派生，不手写**——这是本候选从"搬家"升级为"深化"的唯一途径，因此排期绑定候选 4 之后。迁移用 codemod，`i18n.test.ts` 的扁平键集相等断言作安全网，CJK 审计口径不变。

**收益**：锁步编辑拆散（每次文案改动只触碰相关文件）；错误键单一来源；新增"孤儿键检测"。

**风险**：机械迁移量大但低智；风险主要在键名改动遗漏（由等价断言兜底）。

**验收**
- [ ] 单次文案变更不再强制双文件全量锁步（仅 zh/en 成对）；
- [ ] 孤儿键检测进 CI；用户可见文案零变化（快照 + CJK 审计）。

- **冻结**：命令/查询的结果形状与语义、错误码与文案、`operations` 表内容、UI 文案与布局行为、发布边界（原文件保护、确定性检查优先、网络默认关闭）。
