# Agent 卡片全项目统一设计

日期：2026-09-29
状态：原型已确认；DEV-110 实施、自动化验证及 Windows release 构建完成，真实桌面验收待执行
基线：`ce7e6faa4b9e775d3ec427cb90629aea24c91d7b`

## 目标

让任何 Agent 目录在发现、初始化/重新发现、Agent 管理、批量部署、项目关联、关系治理等入口中都遵循相同的实体身份、品牌/类型合并、共享目录拓扑、状态和能力事实。后端提供一致的目录事实和操作成员映射；前端使用单一卡片投影和呈现规则。用户从任何入口看到或选择同一物理目录时，语义和可执行目标保持一致。

另有一个独立的局部视觉修复：只将初始化/重新发现向导“可选择的兼容性目标”标题上移到与内容框线分离的位置；不遮挡边线，不改变周边间距、颜色、边框、网格、卡片和滚动行为。

## 当前事实与问题

- Agent 列表使用前端 `AgentCardModel`，以品牌、目录角色和目录身份归并类型；其他页面仅部分复用 `AgentPresentation` 或旧的 `AgentCardView`。
- 初始化/重新发现向导把兼容目标压缩成 `AgentView` 后交给 `buildAgentCardViews`，丢失共享引用、物理身份及部分能力/状态事实。同物理共享目录因此可能同时作为品牌目录卡和共享目录卡出现。
- 本地发现工作台由 `buildAgentGroups` 独立归并；其共享目录呈现不消费 Agent 卡片模型的已识别品牌/类型清单。
- 后端批量部署目标查询按物理目标聚类共享目录，但普通目录仍逐逻辑目标生成部署目标；同品牌、同物理目录、不同类型可重复出卡。目标契约只提供单个 `agent_client_id`/profile，不能完整表达普通目录成员类型集合。
- 项目注册和项目详情从发现快照逐逻辑目标生成关联选择项，没有同目录成员归并及类型集合；共享目标也可能重复。
- 当前 Agent 卡片模型会把合并成员的 `supportedModes` 做并集。它没有保留每个成员的能力与可执行目标集合，混合能力可能被错误地呈现为整张卡都支持。
- 技术 ID 仍用于内部成员选择和命令映射；它们必须留在数据层，不得作为可见标题、标签、辅助文案或无障碍名称展示。

## 设计

### 1. 后端统一目录事实投影

在现有发现快照与根目录观察事实之上，提供一个生成绑定的 Agent 目录投影。投影以经验证的物理目录身份作为已有目录的权威分组依据；未验证/待创建候选使用明确标记的候选身份，不能伪装成已验证物理身份。投影为每个目录实体保留：

- 目录角色（Agent 原生、共享、内置、项目）、观察状态、规范化展示路径和身份验证状态；
- 已识别的品牌、各品牌的 Agent 展示类型，以及共享目录与识别该目录的 Agent 之间的关系；
- 类型成员对应的逻辑目标集合；
- 每个逻辑成员自己的可用性、读写状态、部署方式能力、推荐方式和部署事实。

共享目录是独立目录实体。可识别该共享目录的 Agent 作为关联方进入同一投影，不复制共享目录实体。品牌是否显示由已识别根目录事实决定。项目目录保留项目身份，不误归类为 Agent 目录。

该投影表达领域事实与稳定身份，不包含本地化文案、图标、用户界面顺序或 JSX/CSS。命令与查询仍由后端按安全事实裁决，不因卡片合并而放宽能力或权限。

### 2. 前端单一卡片投影与 presenter

由一个共享纯函数将后端投影转成 `AgentCardModel`，由统一 presenter 映射品牌和用户视角类型徽标。所有入口可按场景排序、过滤或分步展示，但不得自行改变身份、合并、共享目录或类型规则。

卡片身份规则：

1. 同品牌、同物理目录、不同类型合为一张卡，并显示类型集合。
2. 不同物理目录分别成卡；字符串路径拼写相似不覆盖已验证物理身份。
3. 共享目录只形成一个独立实体卡，关联品牌与类型作为其徽标/提示。
4. 不存在已识别 Agent 根目录时不显示品牌卡；根目录存在但技能目录待建时显示待创建状态。
5. 内置目录保持只读角色，不与普通目录混为一张可部署卡。

选择一个合并卡片时，前端把操作展开为该卡片所代表的逻辑目标集合。能力保留在成员粒度；不得通过并集把只对部分成员成立的派发方式标成全卡支持。提交前仍由后端逐成员验证能力、权限、路径状态和用户确认。

### 3. 消费入口与迁移边界

同一投影/模型用于：

- Agent 列表、详情中的目录矩阵及共享目录关联呈现；
- 初始化和设置重新发现兼容目录卡；
- 本地发现工作台的可用/不可用目录列表；
- 批量部署目标选择和待建目录确认；
- 项目注册及项目 Agent 关联选择；
- 关系治理、关系图谱、部署、技能详情等涉及 Agent 身份的呈现。

关系图仍维持明确拓扑“Skill → 共享目录 → 可识别 Agent”；共享目录卡片模型不替代实际关系图的关系边。只显示身份的上下文不强制改成选择卡，但必须复用相同 presenter 与用户可读类型事实。

删除或改为薄适配层的入口专有归并逻辑包括 `buildAgentGroups`、向导临时 `AgentView` 转换，以及部署/项目选择器按逻辑目标逐条产生的重复卡片。场景适配只能改变展示排序/过滤和操作可用性，不能复制另一份身份算法。

### 4. 生成契约与兼容

Rust 查询/命令结构是契约来源；修改后通过仓库绑定生成工具更新 TypeScript，不手工维护重复接口。现有数据库发现快照及旧持久化记录继续通过适配层读取。待建/不可访问/失效链接等状态必须显式保留。部署和项目操作继续使用现有稳定目标 ID 作为内部映射，不把用户界面卡片 ID 当作授权或文件系统身份。

## 验收标准

- 对同一组发现事实，从 Agents、初始化/重新发现、发现工作台、批量部署、项目注册/详情生成的卡片，在身份、品牌、类型合并和共享目录数量上保持一致；允许各场景的状态过滤不同，但须明确说明过滤原因。
- 同品牌同物理路径跨类型只出现一张；不同物理路径分别出现；共享物理目录仅一张，并只展示已识别品牌及其类型。
- 选中合并卡片后，后端执行的逻辑目标集合与卡片成员完全一致；取消、部分不可用、重试和重复创建不会丢目标或误选目标。
- 混合部署能力不会显示成所有成员均支持；不支持的方式不能提交；待建目录必须确认后创建并重新观察物理身份。
- 无品牌/类型裸技术 ID、绝对个人路径重复拼法或后端枚举作为独立可见标签；辅助技术说明和无障碍名称也使用用户可读身份。
- 共享关系图继续显式保留“共享目录”节点及 Agent 关联边。
- 向导标题上移且与边线分离，边线保持可见；其它视觉和交互保持不变。
- 更新生成绑定、前后端单元/集成覆盖、浏览器流程验证及开发状态、自动化说明、验收矩阵；真实桌面检查仍单独记录，不能由自动化代替。

## 风险与开放设计点

- 一个物理目录可对应多条逻辑目标，操作层需一致处理部分能力/部分失败；该场景不能由卡片视觉归并掩盖。
- 待创建目标尚无物理身份。合并候选只能依据后端明确的候选身份，不能仅凭未经验证的路径文本合并不同 Agent 根目录。
- 发现快照、部署目标查询和项目关联写入当前使用不同 ID 空间；实现规格需逐个列出读写映射，保证投影成员与命令参数可往返。
- Windows junction、macOS symlink、不可访问目录、失效链接、大小写和路径分隔符需要跨平台夹具与真机人工验收。

## 实施分期建议

1. 固化统一后端投影契约和成员/能力映射，生成 TypeScript 绑定。
2. 将前端卡片模型改为只消费该投影，补身份归并、共享拓扑和成员级能力覆盖。
3. 迁移向导、发现工作台、部署选择和项目关联，再检查 Agent 详情、关系治理、图谱、技能/概览等全部消费点。
4. 做跨入口同快照一致性验证、路径/权限/取消/重复创建/恢复测试及人工验收清单更新。
5. 独立提交向导标题上移的局部视觉修复，并按上述范围完成前端构建与桌面验收记录。


## 2026-09-30 补充裁决：Agent 目录角色与卡片位置

本节覆盖前文将 Agent 工作区目录统称为项目目录的表述，并记录用户确认的卡片原型与 DEV-110 实现要求。

### 目录角色

保留目录角色维度，不额外增加含义重复的目录类型字段。普通 Agent 目录按路径用途分为：

| 角色 | 含义 | 卡片徽标 |
| --- | --- | --- |
| Agent 内置目录 | Agent 自带技能目录；随 Agent 软件更新，v0.2.0 只读且不可派发 | 琥珀色“内置”文字徽标 |
| Agent 用户目录 | 用户范围内的 Agent 技能目录，按实际文件权限读写 | 蓝色“用户”文字徽标 |
| Agent 工作区目录 | Agent 在其工作空间内使用的技能目录，包括既有 profile 中以 project scope 声明的此类路径 | 紫色“工作区”文字徽标 |

Hermes 的 `{project_root}/.hermes/skills` 与 OpenClaw 的 `{project_root}/skills` 属于 Agent 工作区目录。不能仅因发现目标 scope 为 project 而将其排除出 Agent 卡片。独立注册的项目实体及其目录遵循另一套模型，本轮不调整；二者不得混为同一种卡片。

共享目录保留独立目录实体与卡片语义，不改为普通品牌目录角色；同一物理共享目录的投影按物理身份分组，不因用户/工作区目录角色差异重复成卡。Agent 是否支持共享目录是单独的能力维度，不能由当前品牌卡是否为共享目录推断。能力事实与共享目录当前是否存在、关联品牌是否已识别分别处理。

目录角色不代替 readable/writable 权限事实；普通用户或工作区目录也可能不可写。文字徽标与说明由统一 presenter 产生，不将内部枚举直接展示。项目实体仍遵循独立模型，不作为 Agent 卡片。

### 卡片原型布局裁决

沿用现有卡片视觉样式，仅统一尺寸和元素位置；本原型已确认并按下列规则实施。

- 品牌位于顶部左侧，客户端展示类型徽标位于顶部右侧；类型较多时在顶部预留区域内右对齐换行。已派发与部分派发状态图标位于平台类型徽标左侧，与平台类型作为一个整体右对齐。
- 目录角色以文字徽标显示，固定在品牌下方、Skill 目录上方：用户用蓝色，工作区用紫色，内置用琥珀色；文字和悬浮说明共同表达含义。
- 支持共享目录使用“支持共享目录”文字标记，放在目录标签行右侧；不占用底部派发方式图标区域。
- Skill 目录标签与实际路径组成固定区域，整体靠近底部派发方式行。
- 底部两个能力图标（复制、链接）固定在左侧，仅通过图标颜色区分能力：支持为绿色，不支持为红色；所有图标均无底色，不以推荐方式增加底色。解释文字位于同一行右侧并右对齐。长说明截断并提供完整提示，不能撑高卡片。
- 共享目录关联品牌 Logo 位于顶部右侧，允许右对齐换行；上部预留区域与下部路径、底栏隔离。固定展示前四个品牌，其余以“+N”标记收纳，并由标题和无障碍名称说明完整品牌列表，不能挤压下部内容。
- 卡片高度统一为 176px，网格最小列宽统一为 21rem；不同入口的选择框和场景操作不得改变主体信息位置。顶部身份、角色、路径与底部能力行使用固定网格区域。

### 当前实现差距

DEV-110 实现将 scope=project 的 Agent 发现目标作为“工作区”角色投影；另行注册的 Project 实体仍走项目模型并从 Agent 卡片过滤。共享目录实体由 `is_shared_directory` 表达，Agent 对共享目录的支持能力由 `supports_shared_directory` 独立表达，不能从当前卡片是否为共享目录推断。相关 Rust/TypeScript 生成契约和 Agents、初始化、发现、单项部署、批量部署入口已同步调整；自动化通过后仍需 Windows/macOS release 真机验收。


### 2026-09-30 最终原型补充：复制与链接

卡片只显示复制与链接两个无底色图标，支持为绿色，不支持为红色。悬浮与无障碍名称分别使用“支持复制导入”“不支持复制导入”“支持链接导入”“不支持链接导入”。

图标表示 SkillHub 当前可提供的导入能力：红色也包含尚未确认的 Agent 能力、宿主探测限制和内置只读边界，不代表已验证 Agent 永远无法读取链接。共享目录读取支持与链接导入支持分别表达。

DEV-111 补充：向导复选框右侧的文字包裹层必须占满剩余宽度，不能按内容的固有宽度收缩；外框、标题、路径和底栏的等宽检查必须覆盖短品牌、待创建和长路径。21rem 为网格最小列宽，空间不足时换成单列；176px 固定卡片高度保持不变。

后端保留复制、符号链接、目录联接三种执行方式及成员粒度能力。卡片展示层先计算成员共同支持的执行方式，再把符号链接和目录联接归并为链接能力；共同方式中至少有一种链接方式才显示支持链接。提交阶段仍按平台、权限、目录状态与成员能力选择并校验实际执行方式，不通过卡片合并放宽权限。

Agent 用户目录与工作区目录均支持正常读写流程，受实际权限约束；内置目录通常随 Agent 软件更新，v0.2.0 只读，不提供写操作。豆包工作、OpenClaw、Hermes 的工作区目录不能因名称或路径中含 workspace 而误归为内置目录。

## 2026-10-01 增量裁决：导入兼容性红绿灯与本机验证闭环（DEV-112）

本节覆盖前文仅按宿主能力交集绘制红/绿图标的规则；卡片尺寸和元素位置沿用 DEV-110/111。

- 复制、链接两个无底色图标均使用红绿灯：确认支持绿，待验证黄，确认不支持红；内置只读两个图标均红，悬浮文字说明只读禁用。
- Agent 读取兼容性与宿主创建能力分别建模。前者按复制、符号链接、目录联接三种底层方式记录；前端合并为复制/链接两个图标。链接至少有一种共同确认支持的方式为绿，否则有待验证为黄，全部明确不支持为红；合卡不能拿不同成员分别支持的方式拼成一种所有成员都支持的方式。
- 实际可提供派发方式仍取兼容性与宿主能力交集，保留现有预览、目录与链接创建检查和回滚机制。待验证不能成为正式派发授权，也不能因一次文件创建失败被更新成 Agent 不支持。待验证的计划失败通过统一 presenter 明确指向待处理。
- 新注册自定义 Agent 的路径授权与兼容性是两件事；默认三种方式待验证。已有内置声明中的未确认原因映射为待验证，没有公开本地入口的客户端仍不提供派发；未收录客户端不再仅凭宿主能力开放派发。
- 待处理由当前目录投影派生，每个逻辑目标/底层方式只保留一个事项。仅对存在、可读、非内置目录生成验证项；macOS 不生成 Windows 目录联接验证项。复制、符号链接、目录联接分别确认，不能从一次链接方式成功推断另一种方式也成功。
- 用户自行使用无敏感内容的测试 Skill：确认入口可读取→在真实 Agent 中确认发现和加载→清理测试入口并保留源文件→填写版本及证据。待处理和 Agent 完整详情页均可记录“确认支持/确认不支持/暂未确定”；后者保留待办。明确结论必须勾选已检查 Agent 读取结果，否定结论还必须排除创建、权限和路径问题。该入口不自动运行 Agent、不自动制造未知兼容的生产派发。
- 本机覆盖记录复用持久化键值存储的专用命名空间，不改写内置 JSON，也不自动上传或影响其他用户。按操作系统、逻辑目标与目录身份隔离；声明或自定义 profile/目录身份变化使旧记录失效。记录声明的 Agent 版本、说明和时间；以不同版本重新确认时清空旧版本的其他方式结论。当前不自动探测所有 Agent 的升级版本，用户升级后需从详情页重验或标回待验证。
- Codex 运行时只加载 openai.json。遗留 codex.json 的终端目录联接声明与其对齐，并将旧 codex.cli 持久化身份解析到有效的终端声明；保留桌面端与终端端的独立兼容性。Windows 本机 app-server 扫描证据确认 CLI 0.154.0 和桌面自带 0.159.2 可发现并启用目录联接测试 Skill；此证据不等于桌面界面和模型调用验收通过。
