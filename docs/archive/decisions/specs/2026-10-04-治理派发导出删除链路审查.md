## 结论

未发现 Critical。发现 3 项 P1、3 项 P2。派发、目标身份复核、删除影响预览、单技能导出和集中管理主流程均有真实 facade/native command/Rust 路径；但桌面 UI 单测大多 mock facade，不能证明真实 OS 文件操作和权限成功。根任务另有 Rust 1338 项通过的报告；本分区未复跑。

## 优先级与最小整改依赖

1. **P1 回收共享目标与 fail-open 影响预览**：关系预览的查询结果应成为提交契约的一部分，后端基于最新共享消费者事实强制决策；影响读取失败/未完成时禁用确认，并在准备过期时要求刷新。先统一单项、批量与删除使用的共享实体/决定映射，再改 native binding 与 UI；用两个消费关系指向同一物理目标的原生集成测试，验证只处理一次、全部消费者可见、失败不越权。
2. **P1 删除部分成功无法恢复**：把多部署删除改为逐项可恢复执行：稳定幂等操作 ID、逐项成功/失败结果与可重试状态；文件和 DB 状态需有可恢复边界，重试前重新核验物理目标和版本，禁止将未知/已改变目标当作同一对象。增加中途文件失败、DB 标记失败、多目标重试及权限拒绝测试。
3. **P1 导出资产漏扫**：安全扫描应接收将要导出的版本完整文件集合，输出包含文件路径的敏感发现；不确定或读取失败应停止创建或要求显式确认。测试至少覆盖 `.env`、脚本/配置资产、正文无敏感词的情况。
4. **P2 导出预览过期**：把确认按钮绑定到预览输入快照/版本 ID；主体、版本范围、格式、目录任一变化即清空旧决定并重新预览；应用层对预览 token 或哈希作一致性校验。
5. **P2 详情入口与删除影响名称**：按规范补全头部动作且保留身份区版式；删除准备查询 `list_deployment_targets` 出错时，目前 `removal/nativeApi.ts:84-105` 捕获异常后以内部 target ID 代替名称并仍可继续确认。最小整改是对影响范围无法读全时 fail-closed，或将未知目标显著列出并要求专门处理，不能让技术 ID 充当可理解风险描述。
