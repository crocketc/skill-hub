# SkillHub LLM 供应商兼容矩阵（2026-09-13 核验）

状态：现行有效。代码基线：分支 `codex/acceptance-optimization-2026-09-13`，供应商能力实现提交 `5b10f9b`/`a6910e3`/`d06a9a4`/`4218e96`/`cb6f08f`/`2d2b4f8`/`d8a88cc`。

支持级别定义：

- **已支持**：契约自动化测试 + 真实服务验证均通过。
- **兼容**：契约自动化测试通过，真实服务验证未完成。
- **实验性**：部分能力通过或存在已知差异。
- **未验证**：证据不足，不宣传支持。

本表与《用户配置与隐私说明-2026-09-13.md》配套阅读；技术架构见《架构决策-2026-09-10.md》。

## 1. 四层契约（本表的组织方式）

一次请求的行为由四层共同决定，任何一层都不再单独决定"用什么参数发请求"：

1. **传输协议（Transport protocol）**：只描述 HTTP 线形状——URL 后缀、认证头、响应信封。取值：`open_ai`、`open_ai_compatible`、`open_ai_responses`、`anthropic`、`gemini`、`azure_open_ai`。
2. **供应商/产品线兼容档（Compatibility profile）**：描述"同一协议下不同产品之间"的差异——结构化输出机制、推理开关、模型目录、凭据策略。共 20 个内置档 + `generic` 兜底。
3. **结构化输出策略（Structured output strategy）**：`json_schema_strict`、`json_schema`、`json_object`、`prompted_json`、`gemini_schema`。
4. **推理/思考策略（Reasoning policy）**：`provider_default`、`disable_for_structured`、`effort_none_for_structured`。

唯一决策入口是 `crates/skillhub-core/src/llm/compatibility.rs` 中的 `compatibility_policy(profile, protocol)`；请求形状由 `skillhub-adapters` 的 `plan_request()` 纯函数产出。**任何请求路径都不允许**按供应商显示名、用户 ID、模型名或 URL 主机名分支选择策略；也不存在运行期"协议自动轮试"或重复请求。切换协议只改变传输层，不会静默改写地址、模型或密钥。

### 1.1 为什么必须分开

- OpenAI 兼容不等于可以下发 `response_format.json_schema.strict`：DeepSeek Chat 只接受 `json_object`；GLM、Moonshot、Qwen、MiniMax 同属"仅 json_object"档。
- DeepSeek 的 Chat 与 Responses 两个面对推理的控制不同：Chat 结构化任务关闭思考，Responses 用 `reasoning.effort = none`；Anthropic 面不注入。
- GLM 普通 API 与 Coding Plan 是两条独立产品线（计费与端点不同），Coding Plan 内部又分 Chat / Responses / Anthropic 三个端点，不能混用。
- 因此"协议类型决定一切"会在真实服务上直接失败；本矩阵按产品线而非按协议列能力。

## 6. 三层连接测试语义

连接测试回答三个**不同**的问题，绝不合并：

1. **服务可达（endpoint）**：地址是否有任何 HTTP 响应（任何状态码都算"可达"），附带耗时。
2. **模型可调用（model）**：一次低 token 的**纯文本**探测，证明认证、模型存在与信封可解析。此级通过即"模型可调用"。
3. **结构化输出兼容（structured）**：按当前兼容档的结构化策略发一次真实结构化请求，证明"真实结构化任务可用"。

判定规则：

- 未执行的层级显示为**未验证**（info 图标），不是失败、更不是成功；模型级未通过时结构化级不下探。
- **模型可调用 ≠ 结构化兼容**：模型能返回纯文本但结构化失败时，只报"结构化输出不可用"的能力警告（warning 图标 + 文案），**不报**"模型协议不兼容"，也不把该供应商标记为不可用。
- 每级都有装饰图标 + 文字，状态不单靠颜色表达。
- 保存配置**不要求**测试成功；测试是诊断动作，不是保存前置条件。

## 7. 凭据、启用状态与部署标签

- **清除凭据**：只删除操作系统凭据存储中的密钥，保留供应商配置；**启用状态不变**（仍显示"已启用"），凭据状态显示"未配置凭据"。清除后模型测试返回凭据错误（`llm.auth_failed` / `credential.unavailable`），不伪装成健康状态。
- **启用/停用**与凭据是两件事；停用的供应商不参与解析（`object_not_found`）。
- **部署标签**：`云端` / `本地`表达的是**部署类型**（是否走网络、是否通常需要凭据），不是健康状态。它不因连接测试结果而改变。
- **本地部署豁免凭据**：Ollama、LM Studio 的认证策略为"无需凭据"；`local` 部署允许 `http`，但仅限 loopback / 私有网段 / 链路本地地址。
- **密钥从不进入数据库或导出文件**：数据库只记录 `llm-provider:{配置ID}` 引用；草稿密钥只存在于表单内存，随表单关闭而清除。

## 8. 已知限制与边界

1. **仅在 Mock 契约层或仅真实未验证的组合不得宣传为"已支持"**：DeepSeek 与 GLM/GLLM Coding 仅 Chat 面通过真实验证，其余面保持"兼容"。
2. **模型目录以实测为准**：供应商目录会变（DeepSeek 已不再列出 `deepseek-chat`）；"获取失败允许手动填写"始终保留。
3. **不自动轮试**：协议/端点错误只报一次，不做事后自动重试其它协议；用户显式切换。
4. **不实现代理/熔断/故障转移**：cc-switch 的代理与路由能力不在本仓库范围，仅作端点参数取证参考。
5. **流式**：所有供应商普遍支持，但 SkillHub 的四个任务均为短请求，统一非流式；流式不在 v0.2.0 范围。
6. **未启用的高级能力**：Anthropic 官方 beta 结构化字段、火山方舟 beta `json_schema` 均未启用，按 `prompted_json` / `json_object` 处理并本地校验。
7. **核验方法**：官方文档直读或服务端抓取；cc-switch 只读取证；真实服务按《人工验收清单》授权后执行。核心断言以 `crates/skillhub-adapters/tests/llm_protocol_contract.rs`、`llm_runner_contract.rs` 的 mock 契约为准。
8. **测试夹具密钥**均为明显虚构值（`sk-test`、`sk-ant`、`sk-glm-fixture` 等），不含真实凭据。

`crates/skillhub-adapters/tests/llm_protocol_contract.rs`（25 个用例）与 `llm_runner_contract.rs`（19 个用例）覆盖：

- 同协议不同供应商获得不同参数（`same_protocol_different_suppliers_get_different_request_parameters`）；
- 纯文本计划不带结构化字段与 Schema；
- 结构化计划跟随**能力策略**而非协议；

- 三级连接测试：模型级为纯文本探测、结构化级为严格探测、端点不可达跳过两个能力级、可达但未授权在结构化级前停止、文本可答而结构化失败仍标记可调用、结构化探测使用兼容档策略。
