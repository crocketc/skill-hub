## 用户裁决项汇总

既有三项裁决均已落成代码并验证：①待办页处置写入接入统一执行桥；②`security` 死代码删除；③关系治理页写入失败留痕（4 处通知抑制全部移除）。

**2026-09-19 新增裁决（部署失败处理批次）：**

1. **恢复动作统一按「回滚」处理；前端文案不出现「回滚」，用户可见词统一为「恢复」。**（已决；2026-09-19 按用户口径补充语义与文案结论）
   - 后端：`/recovery` 的处置固定发 `resolve_recovery { operation_id, action: "rollback_operation" }`，不向用户暴露 `complete_operation` 二选一。`list_recovery_candidates`（`application/src/lib.rs:9310-9339`）仍按契约返回两个动作，UI 只呈现回滚语义的那一个。
   - **语义口径（用户 2026-09-19 明确：「恢复应该是失败了才恢复，成功了就应该是完成」）——成立，且入口已经保证**：`list_recovery_candidates` 只列 `phase ∈ {planned, prepared, applying, verifying, needs_recovery}` 的操作，**`committed` 的操作永远不会出现在恢复页**。所以能进恢复页的按定义都是「没走完」的，用户在恢复页唯一要决策的就是「把这次没做完的改动撤掉」。
   - **「完成并继续」两句必须删掉**：`recovery.heading` 现为「完成中断的操作」/`Finish the interrupted operation`，`recovery.description` 现为「确认操作状态后，再确认恢复并继续。」/`Review the operation state before acknowledging recovery and continuing.` —— 它们描述的是 `complete_operation`（把没走完的操作做到底）的语义，与统一回滚**直接相悖**。改为「恢复未完成的操作」＋「上次的操作没有走完，可能已经写了一半；确认恢复后，SkillHub 会撤销这次未完成的改动，让它回到操作前的状态。」按钮 `recovery.acknowledge`「确认恢复」保留（符合「用恢复、不用回滚」的用词要求）；改键需同步 zh/en 键对称与术语专项测试。
   - **`complete_operation` 保留为后端能力、不上 UI**：将来要做到「校验磁盘通过才允许确认完成」时它才有意义。理由：本批唯一新增的回滚类规则是「落库失败必须回滚磁盘产物」（R-11 修复方向 ②）。该规则生效后仍停在 `needs_recovery` 的只剩「写了一部分、状态不可判定」的情形，**回滚总是安全的默认**；而 `complete_operation`（`lib.rs:9343` 只把 phase 写成 `committed`）不校验磁盘，会把孤儿目录永久确认为「已完成」。
   - **新发现（2026-09-19 核对源码）：只把前端接到 `resolve_recovery` 还不够 —— 「恢复」现在根本不碰磁盘。** `LocalRecoveryBackend::resolve`（`application/src/lib.rs:9341-9368`）只执行 `UPDATE operations SET phase/state`，不删除任何产物；部署路径也从未记录补偿信息（`application/src/lib.rs` 全文无 `inverse` 赋值，实测那次失败部署的 `inverse: null` / `recovery_data: {}`）。所以本批必须补：**恢复 = 撤销磁盘产物 + 结算账目**（见第 4 条），否则「恢复」只是把账目改成 `rolled_back`，用户目录里的半成品仍在。
2. **重复添加的唯一约束修法：按 `① upsert 复用旧行` 落地。**（2026-09-19 补：已逐个核对消费者，两个选项在**用户可见面上没有差别**，差别只在库内卫生 —— 见 R-11「两个修法选项」。因此取不需要 schema 迁移的 ①；若后续确认要在表内保留「逐次添加」的历史行，再改 ②。）实施前先补齐《自动化测试说明》缺口 1 的失败用例。
3. **既有前端用例把已废弃的命令当成了期望值，需同步改正（2026-09-19 决定，执行方自定，不再单独征询）。** `apps/desktop/src/features/operations/nativeApi.test.ts:19-23` 现在断言的正是「会调用 `acknowledge_recovery`」—— 而该命令既未实现（`facade.rs:1474-1490` 断言它返回 `internal.error`）、又按裁决 1 要删除，等于把待删行为固化成期望值。按裁决 1 改成「调用 `resolve_recovery`，`action` 为 `rollback_operation`、`operation_id` 为被选中的那条」，`nativeApi.ts:30-37` 的 `acknowledgeRecovery` 一并改名改实现。（措辞说明：不写成「断言方向是反的」，统一表述为「用例把已废弃的命令固化成了期望值」。）
4. **「恢复」必须真的撤销磁盘产物（2026-09-19 新增，前置已由第 1 条末项确认）。** 在 plan/prepare 阶段把「本次将写入的目标路径 + `runtime_name` + 归属校验」记进 `recovery_data`，`rollback_operation` 据此删除对应条目；不得只改 `operations` 行。验收判据：一次被中断的部署，恢复后目标目录条目数回到操作前，且 `deployments`/`deployment_relations` 无残留。
5. **三项非本轮范围的事项已登记为待开发项**（跨卷端到端写入 → 改在 macOS 补做；J-REL-3 内容判据 → 用户人工补真实素材；「文件夹名 == SKILL.md name」校验 → 集中库侧需先定重名策略）。清单见《开发状态-2026-09-18》「待开发项（backlog）」。

- **日期/系统/构建**：2026-09-19，Windows 11 家庭版 25H2（非管理员、未开开发者模式）；`target/release/skillhub-desktop.exe`。
- **触发**：`BootstrapGate.tsx:99-101` 在 `recovery_state !== "clean"`（**`in_progress` 与 `needs_recovery` 都算**）时阻断**所有**路由，只放行 `/recovery`。命中后应用只能停在阻断页：标题「需要恢复后才能继续」、说明「检测到尚未完成的恢复操作…」、唯一动作是链接「打开操作记录与恢复」。
- **现象**：在 `/recovery` →「备份恢复」页签点「确认恢复」，**必然失败**；页面上直接渲染出 **`[object Object]`**；`recovery_state` 保持非 `clean`，未终结操作**永远清不掉**。
- **根因（三层，均已核对源码与实测）**：
  1. **前端调的是「未实现命令」。** UI 两条恢复路径都只调 `execute_command { acknowledge_recovery }`：`features/operations/nativeApi.ts:35`（`/recovery` 的「确认恢复」）与 `features/pending/nativeApi.ts:61,78`（待办页 recovery 项的「恢复/移除」）。而 application 层**没有 `AppCommand::AcknowledgeRecovery` 的 dispatch 分支**——`crates/skillhub-application/tests/facade.rs:1474-1490` 的用例 `unsupported_operations_return_a_structured_internal_error` **明确断言**它返回 `code = internal_error`、`params.operation = "execute.unsupported"`。也就是说「该命令未实现」是被测试固化下来的现状，而不是偶发故障。
  2. **真正能用的命令前端从未调用。** 能改 `operations` 表 phase/state 的是 `resolve_recovery`（dispatch 见 `application/src/lib.rs:5251`，实现 `LocalRecoveryBackend::resolve` 见 `:9341`）。全前端检索 `resolve_recovery` **只在 `api/bindings.ts` 的类型定义里出现，没有任何调用点**。
  3. **失败渲染成 `[object Object]`。** `features/recovery/RecoveryPage.tsx:113-115` 用 `reason instanceof Error ? reason.message : String(reason)`；Tauri IPC 的 rejection 是**结构化对象**（`{code, params, severity, actions}`），不是 `Error` 实例，于是 `String(obj)` = `"[object Object]"`。同一批 rejection 用 `JSON.stringify` 能得到完整字段，说明对象本身信息齐全，只是渲染方式错了。
- **命令契约实测（2026-09-19 补，`sr-verify.out` 第 15–20 行）**：在同一条 IPC 通道上逐字取到两个命令的返回——
  - `acknowledge_recovery`（UI 实际调用）：`ok=false`，`String(e) = "[object Object]"`，`JSON.stringify(e) = {"actions":["retry"],"code":"internal.error","params":{"operation":"execute.unsupported"},"severity":"error"}` —— 与 `facade.rs:1474-1490` 固化的断言**逐字一致**。
  - `resolve_recovery {action:"rollback_operation"}`（UI 从未调用）：`ok=true`，随后 `recovery_state` 由 `needs_recovery` 变为 **`clean`** —— 反证「唯一可用的解闸命令确实存在、只是没接线」。
- **实测证据（真实 DOM 点击）**：
  - 候选集只有 `e4ffe5d8-…`（phase/state 均为 `needs_recovery`），`latest` 恰好就是它 → 通过 `list_recovery_candidates` 成员校验 → 继续调 `acknowledge_recovery` → **失败** → 页面出现 `[object Object]`，`recovery_state` 仍为 `needs_recovery`（`%TEMP%\skillhub-w6\sr-final2.out` 第 19–32 行）。
  - 未终结操作不是 `latest` 时（早前 `ff0c7362`），失败发生在成员校验处，报硬编码英文 `recovery operation was not found`。
  - **两种情形都失败** → 该入口**无条件不可用**（此前把它写成「竞态型、条件可达」是误判，现据根因更正）。
- **影响**：命中即**硬卡死**——BootstrapGate 阻断全部路由，UI 无任何出路，只能改库或走 IPC。而 R-10 表明**一次普通的失败部署**就会产生 `needs_recovery` 操作，所以这不是罕见路径。**故升级为发布阻塞。**
- **修复方向（①③ 已由裁决固定，2026-09-19）**：
  1. **前端改调 `resolve_recovery`，动作统一按回滚。** 用户可见文案用「**恢复**」、**不出现「回滚」**（后端命令与 `RecoveryAction` 枚举仍是 `rollback_operation`）。不向用户暴露 `complete_operation` 二选一；`list_recovery_candidates`（`application/src/lib.rs:9310-9339`）按契约仍返回两个动作，UI 只呈现回滚语义那一个。裁决理由与连带文案改动见本文件「用户裁决项汇总」第 1 条。

  3. `RecoveryPage.tsx:113-115` 的失败渲染改走 `describeNativeError`，**禁止 `String(reason)`**；同时把 `/recovery` 的候选列表从「只处理 `latest`」改为「列出 `list_recovery_candidates` 全部候选、逐条选择」。

  - **提交后的真实结果**：`commit ok=true`、`committed=false`、`error_code="deployment.target_exists"`，结构化错误为 `{"code":"deployment.target_exists","severity":"error","params":{},"actions":["choose_another_name"]}` —— 注意**只有一个动作、且不带路径**，与 R-10 那次（`params.path` + `choose_another_name`/`inspect_target` 两个动作，来自 `filesystem.prepare` 的写盘前拒绝）是**不同的来源**。
  - **磁盘却被改了**：提交前 `dest free = true`，提交后 `.claude/skills` 由 **20 → 21**，`find-skills/` 内含 `["SKILL.md"]`（受管复制的完整产物）。**即：一次被报为「失败」的操作，往用户的 Agent 目录写进了东西。**
  - **账目没有对应行**：`deployments` 表**不新增行**（仍只有那条 `state='removed'` 的旧行），操作记为 `needs_recovery` → 下一次启动直接进恢复闸门（叠加 R-9 = 打不开应用）。已实测：`recovery_state after commit = needs_recovery`，杀掉进程重新启动后应用停在阻断页、技能库界面的搜索框都不存在。
  - **孤儿在扫描前不可见**：`get_skill_relationship_graph(find-skills)` 只返回两条边——`managed_copy → anthropic.claude-code`（`active: false`，旧的已移除记录）与 `unknown → deepseek-harness.web`（`active: true`），**没有**指向新建的 `.claude/skills/find-skills` 的边。应用也没有清理入口（`reconcile` 命令族需要已知的 `deployment_id`）。
  - **根因（已核对源码，两处独立缺陷）**
    1. `crates/skillhub-storage/src/database/deployment_repository.rs:63-95` 的 `insert_sync` 是**裸 INSERT**，而 `deployments` 表带 **`UNIQUE(target_id, runtime_name)`**；移除部署走的是 `mark_removed_sync`（`UPDATE state='removed'`，**保留行**）。于是同一个 (目标, runtime_name) **第二次**添加必然撞唯一约束 —— 换句话说：**「成功移除」一旦发生过，同一个 Skill 就再也添加不回这个目标了。**
    2. `insert_sync` 的 `map_err(database_error)`（`deployment_repository.rs:355-369`）把 SQLite 约束码 **2067（SQLITE_CONSTRAINT_UNIQUE）** 映射成 `ErrorCode::TargetExists` + 单个 `choose_another_name` 动作 —— 与实测错误形状吻合。**这是唯一在部署链上产出「单动作 TargetExists」的位置。**
    3. `LocalDeploymentBackend::apply_target`（`crates/skillhub-application/src/lib.rs:507-533`）的次序是 **先 `filesystem.prepare`/`apply` 写盘、后 `insert_sync` 落库**，且写盘与落库之间**没有回滚**：库写失败时文件已就位 → 孤儿。
- **影响**：这是一条**必然发生**的路径（任何「添加 → 移除 → 再添加」都命中），后果是「用户目录被写入 + 应用记成失败 + 下次启动被闸门锁死」。**发布阻塞。**
- **什么场景会撞上（2026-09-19 澄清；回答「重复添加的修法是什么场景，不太明白」）**：不是「同一时刻点两次添加」，而是**时间上先后发生的「添加 → 移除 → 再添加」**，全流程都是正常操作：
  1. 用户把 Skill `find-skills` 添加到 Agent `Claude Code`（目标目录 `~/.claude/skills`）→ 成功。`deployments` 新增一行，`(target_id='fs:volume-537021033-…', runtime_name='find-skills')` 被这一行**永久占用**。
  2. 用户后来从该 Agent 移除它 → 目录被删掉，但库里那行**不删**，只把 `state` 改成 `removed`（`mark_removed_sync`，`deployment_repository.rs:97-126` 的 `UPDATE … WHERE state IN ('deployed','active')`）。**唯一约束上的占用没有释放。**
  3. 用户过几天改主意，再添加**同一个** Skill 到**同一个** Agent → 磁盘上是**干净的**（目录不存在），`get_deployment_plan` 也报 `change=create / conflicts=[]`，但 `insert_sync` 的裸 `INSERT` 撞上 `UNIQUE(target_id, runtime_name)` → 报 `deployment.target_exists`。
  这条路径**不需要任何异常条件**：只要用户曾移除过一次，就等于「这个 Skill 再也装不回这个 Agent」。直白说：**「移除」不是「删除记录」，而是「把行标记为已移除」，而被标记的那行仍然占着那个位置。** 本机现在的库正好停在第 2 步（`deployments` 仅 1 行、`state='removed'`、`runtime_name='find-skills'`），因此现在再添加一次 `find-skills` 到 Claude Code **必然复现**。
- **用户可见后果（2026-09-19 逐个核对消费者后补，回答「这两种方案对用户有什么影响」）**：**两个选项在用户可见面上没有差别**，差别只在库内卫生。核对结果：
  - 已经过滤掉 `removed` 的消费者：Agent 页面的计数（`features/agents/nativeApi.ts:29-40` 的 `managedDeploymentStats` 显式排除 `state === "removed"`）、部署关系查询（`application/src/lib.rs:7934-7954` 排除 `Removed`）、退出管理的影响预览（`lib.rs:3575-3583` 只取 `Deployed`）、删除 Skill 的前置检查（`lib.rs:652-658` 只认 `Deployed`）。**这些面上选 ① 或 ② 完全一样。**
  - **唯一会露出差别的地方：数据保护 →「退出管理」的部署关系列表**（`features/backup/DataProtectionPage.tsx:349-362`，数据直接来自 `list_deployments`，后端 `lib.rs:7919-7932` **只按 `skill_id` 过滤、不看 `state`**）。=> 选 **②** 时，每次「添加 → 移除」都会在这个列表里多留一条陈旧行、无限累积；选 **①** 时同一位置最多留一条（就是那条被标记 `removed` 的行）。**这是 ① 优于 ② 的用户侧理由。**
  - 关系表不受影响：`deployment_relations` 的冲突键是 `(agent_client_id, path_key)`（`relationship_repository.rs:503`），是**按路径 upsert**，所以哪怕按 ② 走、每次生成新的 `deployment_id`，也只是把**同一行**的 `relation_id` 改写成 `managed:<新 id>`，不会出现重复边、不会留悬空关系。
  - **注意这条本身是个独立缺陷（已另立 R-12）**：即使在 ① 下，那条 `removed` 行仍会出现在「退出管理」列表里（状态显示为未翻译的英文 `removed`）。这与选哪个选项无关，必须单独修。
- **两个修法选项（2026-09-19 说明；2026-09-19 定：按 ① 落地）**
  - **① upsert 复用旧行（已定）**：`INSERT … ON CONFLICT(target_id, runtime_name) DO UPDATE SET version_id=…, state='deployed', method=…, updated_at=…`，**并保留旧行的 `id` 不覆盖**。语义 =「同一目标上的同一个文件夹名只保留一份记录，重新添加就是把这行重新激活」。改动只在 `deployment_repository.rs::insert_sync` 一处 + 一条用例，**不动 schema、不需要迁移**；保留 `id` 是为了让关系键 `managed:<deployment.id>`（`relationship_repository.rs:367`）保持稳定——移除时 `mark_removed_sync` 已把该关系行标记为移除（`:118-121`），重新添加时同一事务内的 upsert 会把它重新激活，不会留悬空关系、不会产生重复边。
  - **② 分区唯一索引**：把表级 `UNIQUE(target_id, runtime_name)` 换成 partial unique index `CREATE UNIQUE INDEX … ON deployments(target_id, runtime_name) WHERE state <> 'removed'`（SQLite 支持）。语义更贴「只有活跃部署才需要唯一」，但**需要一次 schema 迁移**（既有库要重建表或 drop/recreate 索引），且 `removed` 行会随每次「添加 → 移除」累积、永不回收。
  - 无论选哪个，都必须同时做另两条，否则仍会留下孤儿：**落库失败回滚磁盘产物**（`apply_target`，`application/src/lib.rs:507-533` 目前先写盘、后落库、失败不回滚）；**失败分类**（不可重试的失败记终态，见上一段，与 R-10 同源）。实施顺序（固定，不能颠倒）：先补《自动化测试说明》缺口 1 的失败用例（先红）→ **落库失败回滚磁盘** → **① upsert 复用旧行** → **失败分类** → **恢复 UX 接线 + 恢复时的磁盘撤销**（见「用户裁决项汇总」第 1、4 条）。顺序理由见「用户裁决项汇总」第 1 条末项：先做分类会把必发的失败掩盖成终态，先做恢复接线会让用户看到「已恢复」而目录里还躺着孤儿。
- **日志与截图索引**：`%TEMP%\skillhub-w6\d11c.out`（干净态复现：`dest free before commit=true` → `commit committed=false` → `dest exists=true; skills=21`）、`d11b.out`（同流程下 `params.path` 变体）、`sr7-link.out`（真实 DOM 全流程 + 深链）、`shots-d11c\F1-plan.png`、`F2-result.png`、`F3-operation.png`。
- **结论**：**新发布阻塞**。与 R-9（闸门无出路）、R-10（零写入拒绝被记为 `needs_recovery`）同属「部署失败处理」这一类，建议合并为一个修复批次：**失败分类（终态 vs 需恢复）→ 磁盘/账目一致性 → 闸门可用性**。

- **修复与复验（2026-09-19，按裁决 ① 落地，TDD 先红后绿）**
  - **① upsert 复用旧行（同一位置最多一条）**：`deployment_repository.rs::insert_sync` 由裸 `INSERT` 改为「先按 `(target_id, runtime_name)` 查既有行，命中则 `UPDATE` 该行（**保留旧 `id`**、`state` 回 `deployed`、刷新 `version_id` / `method` / `updated_at`），未命中才 `INSERT`」。表结构未动、无需迁移；保留 `id` 是为了让关系键 `managed:<deployment.id>` 稳定。**`UNIQUE(target_id, runtime_name)` 继续成立，因此同一位置最多一条记录**——「重新添加」是把那一行重新激活，而不是新增行。
  - **② 落库失败回滚磁盘**：`apply_target` 在 `insert_sync` 失败时调用新增的 `roll_back_applied()`（以 `replace_owned` 撤销刚写入的目标、容忍内容不匹配），并把 `path` / `runtime_name` / `requested_mode` / `residue` 注入错误参数 —— **不再出现「文件已落地、账目无行」**。
  - **新增 `remove_residue`**：`DeploymentFilesystem` 新增按部署模式删除半成品的能力（跳过归属证明、路径不存在时幂等），供恢复时撤销使用。
  - **回归护栏**：`facade_deployment_accounting.rs` 新增 `re_adding_a_removed_skill_reuses_the_same_position`（断言仍**只有一行**、`id` 未变、已重新激活、`recovery_state == Clean`）与 `a_storage_failure_rolls_back_the_written_target`（注入 `BEFORE INSERT` 触发器使落库失败 → 断言目标目录不存在、无残留）。
