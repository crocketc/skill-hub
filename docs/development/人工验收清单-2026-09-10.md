## 先说明两个容易混淆的问题

### 1. 为什么重新运行向导不能更换集中库

这是当前产品规则，不是验收环境故障：集中库初始化完成后，库根目录会被锁定。设置页的“重新发现 Agent 与 Skill”只执行只读发现/扫描，不是清空数据，也不是迁移库根目录。

- 首次初始化：使用“初始化向导”选择集中库。
- 已初始化后更换集中库：使用“设置 → 数据保护 → 备份/恢复”迁移，不要使用初始化向导。
- 如果重新发现入口出现激活、完成初始化或部署控件，应记录为文案/交互问题；迁移在 v0.2.0 不属于初始化向导能力，必须使用数据保护流程。

### 2. 如何重新测首次初始化

不要删除原来的集中库或应用数据。先退出源码启动的应用，再把应用数据库目录改名，形成可恢复的隔离环境。

Windows：

```powershell
Stop-Process -Name SkillHub -ErrorAction SilentlyContinue
Rename-Item "$env:APPDATA\SkillHub" "$env:APPDATA\SkillHub.acceptance-backup-$(Get-Date -Format yyyyMMdd-HHmmss)"
```

macOS：

```bash
mv "$HOME/Library/Application Support/SkillHub" \
   "$HOME/Library/Application Support/SkillHub.acceptance-backup-$(date +%Y%m%d-%H%M%S)"
```

然后重新启动源码或安装包。应用会以全新的数据库启动；原来的集中库目录不会被删除。验收结束后，关闭应用，把新生成的 `SkillHub` 目录改名保存，再将带有 `acceptance-backup-` 后缀的目录改回原名，即可恢复原来的测试记录。

每次首次初始化验收都使用新的空目录，例如 Windows `D:\SkillHub-acceptance\library-01`、macOS `~/SkillHub-acceptance/library-01`。不要把个人真实 Skill 目录当作验收目录。

## 通用执行规则

- 每次只执行一条用例；结果只填“通过、失败、阻塞”，未执行保持空白。
- 每条用例记录：平台、系统版本、应用版本、操作步骤、截图/录屏、关键文件路径和问题编号。
- 测试数据使用专用目录、明显虚构的占位凭据和可删除的测试 Skill，不使用真实凭据或个人 Skill 内容。
- 破坏性操作前先复制测试目录；失败后停止后续破坏性操作，保留日志、截图以及文件系统前后状态。
- LLM 用例只使用测试账户或本地模型；测试结束后删除供应商配置和系统凭据。

## 覆盖范围：为什么人工用例只有 27 条

当前 27 条是“必须依赖真实桌面或真实系统能力”的人工用例，不是 v0.2.0 的全部功能用例。v0.2.0 的完整原子目录共有 349 条：

- 325 条自动化候选：通过 Rust、前端组件、契约测试、Playwright E2E 和脚本检查覆盖。
- 27 条真实设备人工用例：就是本文件的 A～G 部分及集中库生命周期新增用例。
- 自动化覆盖的功能包括技能发现/导入、重复与冲突、技能详情与 Markdown、版本与来源更新、Agent/项目、单个与批量部署、删除/解除管理、备份预检与恢复冲突、操作记录、双语/i18n、LLM 设置与四项 AI 闭环、300 Skill 规模和发布就绪检查。
- 不能仅靠自动化证明的内容包括真实文件系统写入、系统凭据存储、真实供应商服务、Windows/macOS 安装与卸载、签名/Gatekeeper/SmartScreen、权限/符号链接、系统缩放、减少动效和真实窗口可用性。

因此，人工验收不是只测初始化，也不是把所有 349 条重新手工重复一遍；应先完成本文件的 27 条，再根据自动化报告和人工失败项补测对应功能路径。
