## 用户裁决项汇总

既有三项裁决均已落成代码并验证：①待办页处置写入接入统一执行桥；②`security` 死代码删除；③关系治理页写入失败留痕（4 处通知抑制全部移除）。

**2026-09-19 新增裁决（部署失败处理批次）：**

1. **恢复动作统一按「回滚」处理；前端文案不出现「回滚」，用户可见词统一为「恢复」。**（已决；2026-09-19 按用户口径补充语义与文案结论）
   - 后端：`/recovery` 的处置固定发 `resolve_recovery { operation_id, action: "rollback_operation" }`，不向用户暴露 `complete_operation` 二选一。`list_recovery_candidates`（`application/src/lib.rs:9310-9339`）仍按契约返回两个动作，UI 只呈现回滚语义的那一个。
   - **语义口径（用户 2026-09-19 明确：「恢复应该是失败了才恢复，成功了就应该是完成」）——成立，且入口已经保证**：`list_recovery_candidates` 只列 `phase ∈ {planned, prepared, applying, verifying, needs_recovery}` 的操作，**`committed` 的操作永远不会出现在恢复页**。所以能进恢复页的按定义都是「没走完」的，用户在恢复页唯一要决策的就是「把这次没做完的改动撤掉」。
   - **「完成并继续」两句必须删掉**：`recovery.heading` 现为「完成中断的操作」/`Finish the interrupted operation`，`recovery.description` 现为「确认操作状态后，再确认恢复并继续。」/`Review the operation state before acknowledging recovery and continuing.` —— 它们描述的是 `complete_operation`（把没走完的操作做到底）的语义，与统一回滚**直接相悖**。改为「恢复未完成的操作」＋「上次的操作没有走完，可能已经写了一半；确认恢复后，SkillHub 会撤销这次未完成的改动，让它回到操作前的状态。」按钮 `recovery.acknowledge`「确认恢复」保留（符合「用恢复、不用回滚」的用词要求）；改键需同步 zh/en 键对称与术语专项测试。
   - **`complete_operation` 保留为后端能力、不上 UI**：将来要做到「校验磁盘通过才允许确认完成」时它才有意义。理由：本批唯一新增的回滚类规则是「落库失败必须回滚磁盘产物」（R-11 修复方向 ②）。该规则生效后仍停在 `needs_recovery` 的只剩「写了一部分、状态不可判定」的情形，**回滚总是安全的默认**；而 `complete_operation`（`lib.rs:9343` 只把 phase 写成 `committed`）不校验磁盘，会把孤儿目录永久确认为「已完成」。
   - **新发现（2026-09-19 核对源码）：只把前端接到 `resolve_recovery` 还不够 —— 「恢复」现在根本不碰磁盘。** `LocalRecoveryBackend::resolve`（`application/src/lib.rs:9341-9368`）只执行 `UPDATE operations SET phase/state`，不删除任何产物；部署路径也从未记录补偿信息（`application/src/lib.rs` 全文无 `inverse` 赋值，实测那次失败部署的 `inverse: null` / `recovery_data: {}`）。所以本批必须补：**恢复 = 撤销磁盘产物 + 结算账目**（见第 4 条），否则「恢复」只是把账目改成 `rolled_back`，用户目录里的半成品仍在。
2. **重复添加的唯一约束修法：按 `① upsert 复用旧行` 落地。**（2026-09-19 补：已逐个核对消费者，两个选项在**用户可见面上没有差别**，差别只在库内卫生 —— 见 R-11「两个修法选项」。因此取不需要 schema 迁移的 ①；若后续确认要在表内保留「逐次添加」的历史行，再改 ②。）实施前先补齐《自动化测试说明》缺口 1 的失败用例。

5. **不要用 CDP 的 `Page.navigate` 进深链**：整页导航后是新文档、资源全部 200，但应用 bundle 不执行（`#root` 为空、零异常、零 console）。**必须走应用自身导航**（点击 `<a href>`，或 `history.pushState` + `popstate`）。

#### 本轮顺带发现的缺陷（非发布阻塞，建议发布前修）

`tauri.conf.json` 的 CSP 写作 `"default-src 'self'; script-src 'self'"`，**没有显式 `connect-src`**，因此 `connect-src` 回落到 `default-src 'self'`，把 Tauri 的 IPC 自定义协议挡在门外。每次启动都稳定复现两条控制台错误：

```
Connecting to 'http://ipc.localhost/query_application' violates the following Content Security Policy
  directive: "default-src 'self'". Note that 'connect-src' was not explicitly set, so 'default-src' is
  used as a fallback. The action has been blocked.
Fetch API cannot load http://ipc.localhost/query_application. Refused to connect because it violates
  the document's Content Security Policy.
console.warning: IPC custom protocol failed, Tauri will now use the postMessage interface instead
```

后果：IPC 每次启动都先失败一次再回退到 postMessage（功能可用，但多一次失败往返、控制台常驻噪音、且丢弃了自定义协议在大载荷上的优势）。Tauri 官方 CSP 文档给出的参考值明确包含 `"connect-src": "ipc: http://ipc.localhost"`。

**修法（一行，`apps/desktop/src-tauri/tauri.conf.json` 第 25 行）**：

```json
// 原值
"csp": "default-src 'self'; script-src 'self'"
// 现值
"csp": "default-src 'self'; script-src 'self'; connect-src 'self' ipc: http://ipc.localhost"
```

`ipc:` 覆盖 macOS/Linux 的 `ipc://localhost`，`http://ipc.localhost` 覆盖 Windows/Android；`'self'` 保留既有同源请求；`script-src`/`default-src` 仍为 `'self'`，安全档位未放宽。

**已修复并复验（2026-09-18，Windows 真机）** —— 证据链三段：

1. **产物内嵌**：重跑 `tauri build --no-bundle`（`cargo build --bins --features tauri/custom-protocol --release`）后，`target/release/skillhub-desktop.exe`（28,176,384 字节，2026-09-18T04:33:04Z）内**按字节 grep 出现且仅出现一次**新 CSP 串。
2. **运行期零噪音**：CDP 挂上后先开 `Runtime.enable` / `Log.enable` / `Network.enable`，再 `Page.reload({ignoreCache:true})` 完整复现一次冷启动 → **`captured diagnostics (0)`、`cspRelated=0`**。原先每次启动必现的两条（CSP 违规 + `IPC custom protocol failed, Tauri will now use the postMessage interface instead`）**均不再出现**。
3. **IPC 真的走回自定义协议**：同一次 reload 的 `Network.*` 事件里出现 3 组 `POST http://ipc.localhost/query_application` → `200`；`window.__TAURI_INTERNALS__.invoke("query_application", {query:{type:"get_application_update_policy"}})` 返回 `keys=type,payload`。回退状态下的版本不会产生这类请求。

**归属确认**：同一次测量里那 1 条 `Failed to load resource: 500` 来自探针自身故意发的畸形请求体（`POST {}`）。把该探针关掉复跑，`captured diagnostics` 由 1 变 0 —— 该条不是产品错误。

  1. 用户把 Skill `find-skills` 添加到 Agent `Claude Code`（目标目录 `~/.claude/skills`）→ 成功。`deployments` 新增一行，`(target_id='fs:volume-537021033-…', runtime_name='find-skills')` 被这一行**永久占用**。
  2. 用户后来从该 Agent 移除它 → 目录被删掉，但库里那行**不删**，只把 `state` 改成 `removed`（`mark_removed_sync`，`deployment_repository.rs:97-126` 的 `UPDATE … WHERE state IN ('deployed','active')`）。**唯一约束上的占用没有释放。**
  3. 用户过几天改主意，再添加**同一个** Skill 到**同一个** Agent → 磁盘上是**干净的**（目录不存在），`get_deployment_plan` 也报 `change=create / conflicts=[]`，但 `insert_sync` 的裸 `INSERT` 撞上 `UNIQUE(target_id, runtime_name)` → 报 `deployment.target_exists`。
  这条路径**不需要任何异常条件**：只要用户曾移除过一次，就等于「这个 Skill 再也装不回这个 Agent」。直白说：**「移除」不是「删除记录」，而是「把行标记为已移除」，而被标记的那行仍然占着那个位置。** 本机现在的库正好停在第 2 步（`deployments` 仅 1 行、`state='removed'`、`runtime_name='find-skills'`），因此现在再添加一次 `find-skills` 到 Claude Code **必然复现**。
- **用户可见后果（2026-09-19 逐个核对消费者后补，回答「这两种方案对用户有什么影响」）**：**两个选项在用户可见面上没有差别**，差别只在库内卫生。核对结果：
  - 已经过滤掉 `removed` 的消费者：Agent 页面的计数（`features/agents/nativeApi.ts:29-40` 的 `managedDeploymentStats` 显式排除 `state === "removed"`）、部署关系查询（`application/src/lib.rs:7934-7954` 排除 `Removed`）、退出管理的影响预览（`lib.rs:3575-3583` 只取 `Deployed`）、删除 Skill 的前置检查（`lib.rs:652-658` 只认 `Deployed`）。**这些面上选 ① 或 ② 完全一样。**
  - **唯一会露出差别的地方：数据保护 →「退出管理」的部署关系列表**（`features/backup/DataProtectionPage.tsx:349-362`，数据直接来自 `list_deployments`，后端 `lib.rs:7919-7932` **只按 `skill_id` 过滤、不看 `state`**）。=> 选 **②** 时，每次「添加 → 移除」都会在这个列表里多留一条陈旧行、无限累积；选 **①** 时同一位置最多留一条（就是那条被标记 `removed` 的行）。**这是 ① 优于 ② 的用户侧理由。**
  - 关系表不受影响：`deployment_relations` 的冲突键是 `(agent_client_id, path_key)`（`relationship_repository.rs:503`），是**按路径 upsert**，所以哪怕按 ② 走、每次生成新的 `deployment_id`，也只是把**同一行**的 `relation_id` 改写成 `managed:<新 id>`，不会出现重复边、不会留悬空关系。
  - **注意这条本身是个独立缺陷（已另立 R-12）**：即使在 ① 下，那条 `removed` 行仍会出现在「退出管理」列表里（状态显示为未翻译的英文 `removed`）。这与选哪个选项无关，必须单独修。
- **两个修法选项（2026-09-19 说明；2026-09-19 定：按 ① 落地）**
  - **① upsert 复用旧行（已定）**：`INSERT … ON CONFLICT(target_id, runtime_name) DO UPDATE SET version_id=…, state='deployed', method=…, updated_at=…`，**并保留旧行的 `id` 不覆盖**。语义 =「同一目标上的同一个文件夹名只保留一份记录，重新添加就是把这行重新激活」。改动只在 `deployment_repository.rs::insert_sync` 一处 + 一条用例，**不动 schema、不需要迁移**；保留 `id` 是为了让关系键 `managed:<deployment.id>`（`relationship_repository.rs:367`）保持稳定——移除时 `mark_removed_sync` 已把该关系行标记为移除（`:118-121`），重新添加时同一事务内的 upsert 会把它重新激活，不会留悬空关系、不会产生重复边。
  - **② 分区唯一索引**：把表级 `UNIQUE(target_id, runtime_name)` 换成 partial unique index `CREATE UNIQUE INDEX … ON deployments(target_id, runtime_name) WHERE state <> 'removed'`（SQLite 支持）。语义更贴「只有活跃部署才需要唯一」，但**需要一次 schema 迁移**（既有库要重建表或 drop/recreate 索引），且 `removed` 行会随每次「添加 → 移除」累积、永不回收。
  - 无论选哪个，都必须同时做另两条，否则仍会留下孤儿：**落库失败回滚磁盘产物**（`apply_target`，`application/src/lib.rs:507-533` 目前先写盘、后落库、失败不回滚）；**失败分类**（不可重试的失败记终态，见上一段，与 R-10 同源）。实施顺序（固定，不能颠倒）：先补《自动化测试说明》缺口 1 的失败用例（先红）→ **落库失败回滚磁盘** → **① upsert 复用旧行** → **失败分类** → **恢复 UX 接线 + 恢复时的磁盘撤销**（见「用户裁决项汇总」第 1、4 条）。顺序理由见「用户裁决项汇总」第 1 条末项：先做分类会把必发的失败掩盖成终态，先做恢复接线会让用户看到「已恢复」而目录里还躺着孤儿。
- **日志与截图索引**：`%TEMP%\skillhub-w6\d11c.out`（干净态复现：`dest free before commit=true` → `commit committed=false` → `dest exists=true; skills=21`）、`d11b.out`（同流程下 `params.path` 变体）、`sr7-link.out`（真实 DOM 全流程 + 深链）、`shots-d11c\F1-plan.png`、`F2-result.png`、`F3-operation.png`。
- **结论**：**新发布阻塞**。与 R-9（闸门无出路）、R-10（零写入拒绝被记为 `needs_recovery`）同属「部署失败处理」这一类，建议合并为一个修复批次：**失败分类（终态 vs 需恢复）→ 磁盘/账目一致性 → 闸门可用性**。

- **修复与复验（2026-09-19，按裁决 ① 落地，TDD 先红后绿）**
  - **① upsert 复用旧行（同一位置最多一条）**：`deployment_repository.rs::insert_sync` 由裸 `INSERT` 改为「先按 `(target_id, runtime_name)` 查既有行，命中则 `UPDATE` 该行（**保留旧 `id`**、`state` 回 `deployed`、刷新 `version_id` / `method` / `updated_at`），未命中才 `INSERT`」。表结构未动、无需迁移；保留 `id` 是为了让关系键 `managed:<deployment.id>` 稳定。**`UNIQUE(target_id, runtime_name)` 继续成立，因此同一位置最多一条记录**——「重新添加」是把那一行重新激活，而不是新增行。
