    - **场景澄清（2026-09-19）**：命中的不是「同时点两次」，而是**正常的「添加 → 移除 → 再添加」**——「移除」只把行标成 `removed`（不删行、不释放唯一约束上的占用），所以**只要用户曾移除过一次，这个 Skill 就再也装不回这个 Agent**。本机库当前正停在该状态（`deployments` 仅 1 行、`state='removed'`），再添加一次必复现。展开说明见《人工验收清单》归档 R-11「什么场景会撞上」。
    - 修复方向（**已定**）：① 唯一约束允许 `removed` 行被重新激活——**按 upsert 复用旧行落地**（`ON CONFLICT(target_id, runtime_name) DO UPDATE`，保留旧 `id` 以稳定关系键 `managed:<deployment.id>`；不动 schema）。备选的分区唯一索引 `WHERE state <> 'removed'` 已排除：两者**用户可见面无差别**，差别只在库内卫生——分区索引会让「退出管理」列表累积陈旧行（第 13 条）；② 落库失败回滚磁盘产物；③ 失败按「可重试 vs 需用户决策」分类（`target_exists` 类记终态）；④ `targets[]` 明细持久化进操作记录；⑤ 恢复 UX 接线 + 恢复时撤销磁盘产物（第 11 条）。**批次顺序固定，不能颠倒**：失败用例先红 → ② → ① → ③ → ④ → ⑤（先做 ③ 会把 ① 的必发失败掩盖成终态；先做 ⑤ 会让用户看到「已恢复」而磁盘仍留孤儿）。

13. **非阻塞缺陷（2026-09-19；见《人工验收清单》归档 R-12）**：数据保护 →「退出管理」把 `state='removed'` 的部署当成「部署关系」列出。**→ 2026-09-19 当日已修复**（消费侧过滤 `removed` + `state` 经 i18n 渲染 + 补渲染用例）。原文如下：后端 `list_deployments`（`application/src/lib.rs:7919-7932`）只按 `skill_id` 过滤、不看 `state`，UI 原样渲染（`features/backup/DataProtectionPage.tsx:349-362`），标签里的 `state` 是未翻译的英文枚举（`i18n/zh-CN/common.json:3074`）。本机 `deployments` 仅 1 行且为 `removed`、磁盘上无该 Skill → 列表会列出一个不存在的部署关系。不写盘、不锁死；修法为**消费侧**过滤 + `state` 中文化 + 补用例。

14. **登记缺陷（2026-09-19 自长期跟踪项转正登记；非独立验收项，无 R 号）**：planner 对目标占用失明——`VerifiedTarget::existing` 硬编码空 `Vec`（`core/src/deployment/model.rs:209`），应用层解析出 verified target 后**从未填充** `existing` → 目标位置已被占用（外来目录、或同一位置已有别的 Skill）时规划仍返回 `change=create / conflicts=[]`，冲突只能拖到 commit 期才以 `deployment.target_exists` 暴露，用户在确认对话框上看到的是「一切正常」。**→ 2026-09-19 当日已修复（TDD，先红后绿）**：`get_deployment_plan` 解析后经 `attach_target_occupancy` 填充占用事实——活跃受管行取自 `deployments`（`managed && state ∈ {deployed, needs_recovery}`；**detached（`managed=0`）与 `removed` 行不算占用**，由磁盘探测裁决），无行覆盖时对 `目标/runtime_name` 做磁盘探测记 `ExistingOwnership::Unknown` → 规划期即拒（`deployment.target_exists` + `choose_another_name`）；commit 期 `filesystem.prepare` 的既有检查保留为「规划-提交竞态」的兜底。用例：`facade_deployment_accounting.rs` 新增 3 条（`a_plan_for_an_occupied_destination_is_rejected_before_commit` / `replanning_a_deployed_skill_reports_noop` / `replanning_after_undeploy_offers_a_clean_readd`）；两条既有 R-10 用例改为「规划通过后、提交前占位」的竞态场景——原场景（规划时已占用）如今在规划期即被拒，走不到 commit，直接沿用会让用例在错误层面通过。
