12. **新发现缺陷（发布阻塞，2026-09-19；见《人工验收清单》归档 R-10/R-11）**：部署失败处理链，两处独立缺陷叠加成「写入用户目录却记成失败」。**→ 2026-09-19 当日已修复**（① `insert_sync` 改 upsert 复用旧行、保留旧 `id`，**同一位置最多一条**；② `apply_target` 落库失败回滚磁盘产物；③ 失败分类改为按残留判定——`residue=false` 记 `rolled_back` 终态且 `recovery_state` 保持 `clean`；④ 目标与路径明细持久化进操作记录；详见 R-10/R-11「修复与复验」）。原文如下：
    - **失败分类错**：`commit_deployment`（`application/src/lib.rs:6046-6087`）丢弃 `DeploymentSummary.targets[]`，只取首个 error code，并对任何非 `ObjectNotFound` 错误一律写 `needs_recovery`；`progress_json` 恒为 `total=0 / object_results=[] / recovery_data={} / result=null` → `/operations/:id` 只有错误码，看不到目标与路径、也没有恢复动作按钮。于是**一次被拒绝的添加就让下次启动进闸门**。
    - **先写盘后落库且不回滚**：`deployments` 表带 **`UNIQUE(target_id, runtime_name)`**，而「移除部署」只 `UPDATE state='removed'`（保留行）→ 同一 (目标, runtime_name) **第二次添加必然**在 `insert_sync` 撞唯一约束（`database_error` 把 SQLite 码 2067 映射成 `ErrorCode::TargetExists`）；此时 `filesystem.apply` 已把内容写进用户 Agent 目录 → **孤儿目录 + `deployments` 无行 + 操作记 `needs_recovery`**。干净态复现：`dest free=true` → `committed=false` → 目录数 20 → 21。
    - **场景澄清（2026-09-19）**：命中的不是「同时点两次」，而是**正常的「添加 → 移除 → 再添加」**——「移除」只把行标成 `removed`（不删行、不释放唯一约束上的占用），所以**只要用户曾移除过一次，这个 Skill 就再也装不回这个 Agent**。本机库当前正停在该状态（`deployments` 仅 1 行、`state='removed'`），再添加一次必复现。展开说明见《人工验收清单》归档 R-11「什么场景会撞上」。
