## 桥的缺省失败描述：`[object Object]` 已成类修掉（第四次更新）

**原问题**：`runTrackedOperation` 的缺省 `describeError` 是 `String(error)`。Rust 侧 `AppError` 经 IPC 传回的是 `{ code, severity, params, actions }`，`String()` 得到 `[object Object]`。凡是**没有显式传 `describeError` 的桥接入口**，失败通知详情（以及顶栏的失败原因）都会显示 `[object Object]`。

**扫描口径与结果**（对 `apps/desktop/src` 下全部非测试源码做括号配对，逐个 `runTrackedOperation(` 调用点检查）：

| 项目 | 数量 |
|---|---:|
| 有实际桥接调用的源文件 | 19 |
| 桥接调用点 | 27 |
| 修复前显式传 `describeError` 的调用点 | 12 |
| **修复前未传 `describeError`** | **15** |
| 其中把 `message` 直接放进 danger 通知的 | 12（受影响最直接） |
| 其中未传 `errorNotice`、用桥默认通知的 | 2（`SkillDetailPage.tsx` 204/244） |
| 其中显式 `errorNotice: () => null` 的 | 1（`RelationshipGovernancePage.tsx` 464，见未收口项 3） |
| 修复后仍显式传 `describeError` 的调用点 | 13（PMD 新增 1；其余 14 处改为依赖可读缺省） |

**修法（改源头，不逐个补）**：缺省描述改为
`describeNativeError(error, translate, "tasks.notices.failureUnknown")`，
但**只对真正的结构化 AppError 生效**——新增形状判定 `isStructuredNativeError`（对象或承载它的 JSON 字符串，且带字符串 `code`）。

**为什么必须加形状判定**：`nativeErrorCode` 会用 `/([a-z0-9_]+\.[a-z0-9_.]+)/i` 从**自由文本**里嗅探「错误码」，于是 `new Error("cannot write skill.md")` 会被嗅探出 `skill.md`，用户的原始消息被替换成「操作未能完成（skill.md）」。这是把可用信息改差。加判定后普通 `Error` 与自由文本原样透出。

**顺带统一**：`projects/ProjectManagedDeployments.tsx` 的 `detach_management` 现在传 `describeError`，使**通知详情与页面内联提示逐字同源**（此前同一失败在通知与页面上会是两句不同文案）。

**验证**：前端全量 165 文件 / 1767 用例通过；`pnpm --dir apps/desktop check`、`i18n-cjk-audit`、E2E 387 全绿。i18n 新增 `tasks.notices.failureUnknown`（zh-CN / en-US 键集对称，含 `{{code}}`）。

## 待办处置入桥：最后一个未收口写入闭合（第五次更新）

**原问题**：`pending/nativeApi.ts` 的处置写入（推迟/忽略/归档，含批量）走页面本地 `batchProgress` 与本地区块提示，未进 `runTrackedOperation`，顶栏与通知中心看不到这些操作——是 Task 4 扫描后**唯一已知未入桥的用户可触发写入**。

**修法**（`0bf619a7`）：`PendingPage` 全部处置入口接入 `runTrackedOperation`：

- 单条处置（转常规/重查/确认恢复/暂缓/忽略）与处理历史的「撤销忽略」走 `instant`：单次同步写入不占在途顶栏，成功/失败都留通知。

- `describeError` 复用页面 `describe`（`describeNativeError` + `pending.errors.generic`），**通知详情与页面局部提示逐字同源**，结构化 AppError 不出现 `[object Object]`。
- 批量「首错即停」语义**不变**；失败后**新增列表刷新**，已完成项如实从列表消失（部分成功可见，不再停留陈旧列表）。
- 边界说明：筛选视图的 `set_ui_preference` 持久化**保持静默**——它是隐式 UI 状态保存，逐次弹通知是干扰；失败已有 `role="status"` 行内提示。

**验证**：新增 5 个桥接测试（先红后绿）：单条成功通知、单条结构化失败通知与页面同源、批量 `phased` 在途投影与计数成功通知（含 `resultSummary`）、批量失败的三端同源与部分成功刷新、撤销忽略成功通知。E2E `workflow-pending` 的失败用例由单 `getByRole("alert")` 改为**双通道断言**（`.sh-pending__action-error` 行内提示 + `notice-danger` 通知，同文案、不含 `[object Object]`）——修复后全量 387 通过。另删除 1 个死代码测试（`security/nativeApi.test.ts` 的 `maps catalog metadata mutations`，随被删导出一起移除）。

## 能力守卫：从「静默 pass」到可观测、可反证的跳过

**原问题（已修复）**：`crates/skillhub-application/tests/facade_relationship_governance.rs` 中 17 处 `available_capabilities().symlink` 守卫在命中时**提前 `return`**。libtest 没有运行时 skip，会把这种早退记为 `passed`；更糟的是它还会捕获通过用例的 stderr，所以连 `eprintln!("skipping: …")` 也看不见。结果是：在无链接能力的宿主上，17 项链路**没有执行任何断言**，却出现在「1098 通过 / 0 忽略」里。

**现在的机制**（`7853ae0f`）：

- 统一的 `skip_or_continue_for_missing_capability(available, requirement, location)`，由 `missing_symlink_capability()`（17 处：夹具自己建符号链接的场景）与 `missing_directory_link_capability()`（1 处：RC-16，只要符号链接或 junction 之一可用就应执行）调用；跳过时打印 `SKILLHUB-TEST-SKIP; 文件:行; 缺少什么能力`。
- 该标记**直接写入进程 stderr 的文件描述符**，绕开 libtest 的逐用例捕获，因此普通 `cargo test` 日志即可计数：`grep -c '^SKILLHUB-TEST-SKIP;' <日志>`。
- `SKILLHUB_REQUIRE_SYMLINK_CAPABILITY=1`：任何跳过都变成硬失败。**在这个开关下全绿，才证明守卫场景真的执行了**。
- `SKILLHUB_TEST_FORCE_NO_LINK_CAPABILITY=1`：负向对照，强制走跳过路径，使这套接线在具备链接能力的主机上也能被验证，不需要改代码。

**本机（macOS）实测**：默认 59 通过 / 0 跳过；负向对照 18 条标记；`REQUIRE` 下 0 跳过；两者叠加 18 失败。因此 Task 12 不再存在「未执行但记为通过」的情形。
