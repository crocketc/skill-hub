### 启动期控制台噪音：CSP 阻断 IPC 自定义协议（2026-09-18 发现，同日修复并加了护栏）

真桌面启动时控制台曾稳定复现（自动化可完整捕获，见《人工验收清单-2026-09-18》R-3 末条）：

```
log[error] Connecting to 'http://ipc.localhost/query_application' violates the following Content Security
  Policy directive: "default-src 'self'". Note that 'connect-src' was not explicitly set, so
  'default-src' is used as a fallback. The action has been blocked.
console.warning: IPC custom protocol failed, Tauri will now use the postMessage interface instead
```

原值是 `tauri.conf.json` 的 CSP 未显式声明 `connect-src`：功能上 Tauri 会回退 postMessage 并继续工作，但每次启动都多一次失败的协议往返。**修复（2026-09-18）**：CSP 改为 `"default-src 'self'; script-src 'self'; connect-src 'self' ipc: http://ipc.localhost"`，重跑 `tauri build` 后在真实 release exe 上冷启动复现测得 **`captured diagnostics (0)`**，且 `Network.*` 出现 3 组 `POST http://ipc.localhost/query_application → 200`。**今后以 release 产物为准的验收应看到 0 条 CSP 错误；若这 2 条错误重新出现，即该配置回归。**

**回归护栏**：`scripts/verify_release_readiness.mjs` 新增两条断言——`connect-src` 必须显式声明且同时含 `ipc:` 与 `http://ipc.localhost`；`script-src`/`default-src` 必须仍为 `'self'`（防止为了修 IPC 而放宽脚本来源）。`scripts/verify_release_readiness.test.mjs` 增加对应用例。红绿已实测：把 CSP 还原成旧值 → `not ok`；改回现值 → `ok`。命令：`node scripts/verify_release_readiness.mjs`、`node --test scripts/verify_release_readiness.test.mjs`（当前 PASS / 10 用例全通过）。

### 产出用于真机验收的 release 产物（2026-09-18 实测口径，两条坑）

1. **必须用 `tauri build`，不能只用 `cargo build --release`。** `tauri build --no-bundle -v` 原样打印出它实际执行的命令是 `cargo build --bins --features tauri/custom-protocol --release`。缺 `tauri/custom-protocol` 时产出的 exe **不内嵌/不伺服前端**：窗口能开，但页面停在 `chrome-error://chromewebdata/`、`document.querySelectorAll('main').length === 0`。本轮实测对照——坏产物 26,348,544 字节 / 正常产物 28,176,384 字节。**任何真机 UI 验收前都应先确认页面 URL 是 `http://tauri.localhost/` 且 `main=1`**，否则后续所有几何结论都是无效的。
2. **`tauri build` 可能卡在 `beforeBuildCommand` 不返回。** 本机实测一次 `pnpm --dir apps/desktop tauri build --no-bundle`：前端步骤已写出 `dist/assets`，但随后 **11 分 18 秒内无 cargo 进程、日志无新增**，最终只能手动终止（`tauri build -v --config` 覆盖后同一仓库 1 分钟内正常完成）。规避法是分两步：

   ```bash
   pnpm --dir apps/desktop build
   pnpm --dir apps/desktop tauri build --no-bundle --config '{"build":{"beforeBuildCommand":"echo frontend-already-built"}}'
   ```

   注意前端产物哈希不变时（例如只改 `tauri.conf.json`）也要**重跑一次 `tauri build`**：CSP、图标、窗口配置都是编译期内嵌的。

### 部署链路的自动化覆盖缺口（2026-09-18 登记，重要）

本机 Windows 实测 **142 个测试目标 / 1098 通过 / 0 失败**，但一次真实「添加到 Claude Code」两次提交都失败（详见《人工验收清单-2026-09-18》R-6）。1098 全绿与真机必失败并存，说明这段链路的断言强度不足，缺口有三处：

1. **没有任何测试真的去建物化目录。** `materialized_source()` 的物化路径含 `sha256:` 冒号，Windows 建目录必失败（`WinError 267`），但 macOS/Linux 上 `:` 合法，所以跨平台跑都绿。缺一条「物化目录路径在 Windows 上可创建」的断言（可直接对 `LibraryPaths` 派生出的路径做断言，或断言路径分量不含 `:`）。
2. **没有端到端的「部署后必须能读到部署记录」断言。** `deployments.target_id` 的外键指向生产从不写入的 `targets` 表；现有部署相关测试都在夹具里**手写** `INSERT INTO targets`（这正是全仓 `INSERT INTO targets` 只出现在测试中的原因）——夹具替生产补了那一行，于是外键永远不报错。缺一条从「新逻辑目标模型解析出 target」到「记录落库」的用例，且该用例**不得**预置 `targets` 行。
3. **没有测试覆盖「Agent profile 声明的能力」与「部署路径实际使用的能力」一致。** `builtin_profiles.rs` 断言了 profile 数据本身（含「所有客户端 `junction` 必须为 false」，且这条断言目前是绿的），但没有任何非测试代码读取它，于是产品不变量成立、部署行为却违反它。缺口是「行为层面」的用例，不是数据层面的。

**不要用放宽断言或加延时来掩盖**；这三条都应按 TDD 补成失败用例再修实现。
