## 自动化命令

| 用途 | 命令与注意事项 |
| --- | --- |
| Rust 单元／集成 | 定向 `cargo test -p <crate> --test <测试文件>`；全仓 `cargo test --locked --workspace` |
| 前端单测 | 全量 `pnpm test:frontend`；定向 `pnpm --dir apps/desktop exec vitest run <受影响测试>`。必须在 `apps/desktop` 下运行 vitest，从仓库根会解析到无 jsdom 配置的 vitest |
| 前端检查与构建 | `pnpm check:frontend`（ESLint 与 TypeScript）、`pnpm build:frontend`、`pnpm --dir apps/desktop check` |
| 浏览器 E2E | 必须用根目录脚本 `pnpm test:e2e <spec>`（带 `--config=tests/e2e/playwright.config.ts`）。直接 `npx playwright test` 不加载 baseURL，会大面积报「Cannot navigate to invalid URL」——是调用方式错误，不是产品缺陷 |
| 发布检查 | `pnpm verify:release`、`pnpm test:release`、`node scripts/verify_atomic_test_catalog.mjs`、`node scripts/verify_frontend_lifecycle_scripts.mjs` |
| 生成绑定 | 临时设置 `SKILLHUB_WRITE_BINDINGS=1` 运行 `cargo test -p skillhub-desktop generate_bindings`，完成后移除该临时变量并核对生成差异；绑定只能由生成工具更新，不手写 bindings.ts |
| Windows release 构建 | `pnpm --dir apps/desktop tauri build --no-bundle`（产物 `target/release/skillhub-desktop.exe`，不提交 Git，供真机验收使用） |
| 本地 CI | `pnpm ci:local` 十项：fmt、deny、clippy、Rust 全仓、冻结安装、生命周期、audit、check、前端单测、构建（保留既有 chunk 提示） |
| 空白检查 | 最终整合提交前 `git diff --check` |

## 覆盖范围与验证边界

自动化覆盖：

- Rust core／application／storage 的领域、facade、存储与迁移测试。
- 前端组件与 nativeApi 契约单测；DEV 预览路由与 mock 门面下的浏览器 E2E（页面契约与几何）。
- 发布检查与原子测试目录一致性校验。

自动化不能证明：

- 真实桌面通过。浏览器预览、预览 HTTP 200、自动化通过均不代表 Windows/macOS 桌面通过；人工验收只按[人工验收清单](人工验收清单-2026-09-30.md)执行并记录。
- 原生文件与权限事实。真实用户目录与 Agent 文件保护、真实权限／只读目录、跨卷行为、真实窗口／主题视觉、长路径与批量耗时、通知中心人工可读性不在自动化覆盖内。Windows 目录联接与 macOS 符号链接的真实落盘与权限取证需真机：能力不足的环境中原生链接场景由守卫提前跳过，测试命令成功不等于原生场景实际运行。
- 10 月 4 日静态审查发现的生产链路缺口（技能保存、版本采用、来源治理、共享删除、导出等）尚未实施，E2E 全绿不证明这些链路完成。缺口依据见[抽屉详情技能链路审查](../superpowers/specs/2026-10-04-抽屉详情技能链路审查.md)、[内容版本安全链路审查](../superpowers/specs/2026-10-04-内容版本安全链路审查.md)、[治理派发导出删除链路审查](../superpowers/specs/2026-10-04-治理派发导出删除链路审查.md)、[画像来源导航链路审查](../superpowers/specs/2026-10-04-画像来源导航链路审查.md)，工作包划分见实施计划。
- mock 与真实持久化分开记录。E2E／浏览器测试使用 DEV 预览路由与 mock 门面，只证明前端契约与几何，不能证明原生 IPC 与数据库的真实往返；浏览器只核界面、导航与原型取消，不证明原生写入，mock 成功不证明生产 facade 完整。生产链路须另用真实应用域＋临时库持久化测试分别验证与记录。
- FB-003／FB-006／FB-007 相关链路未关闭：导入安全发现分级与说明、检查结果按导入版本持久化、批内重复／同名冲突在提交前明确呈现。现有记录未证明已解决，10 月 4 日 CI 通过不关闭这些未覆盖链路；先按实施计划 K0 核现行源码、历史裁决、测试与素材，再确定收口方式。
- 部分真机时序无法由自动化稳定制造：DEV-101 真实进程崩溃时序按流程 I 真机验收；自定义 Agent 真实登记（原生文件选择器授权）、真实目录替换后的身份变化拦截、部署／解除落盘属流程 L 真机范围。

## 验证纪律

- 行为变更采用 TDD：先写失败测试，再实现最小行为，最后重构；不降低断言、不删除测试、不假成功、不增加任意延时。
- 开发阶段按影响范围定向验证：只运行改动模块、受影响调用方与关联流程的测试；涉及共享组件、跨模块契约、数据库迁移、依赖或构建配置时，先识别受影响范围再扩大相关回归；无法可靠限定影响范围时才提前执行全量测试并说明原因。
- 相关测试通过且代码未再变化时，不重复运行同一套测试；出现新改动、失败或未解决风险时，再补充必要验证。回报须写明本轮测试范围、结果与尚未验证的边界，定向通过不得写成全量通过。
- 发布前必须在最终整合提交上执行全量验证：`pnpm ci:local`、`pnpm test:e2e`、发布检查与 `git diff --check`，并处理失败；定向通过不能替代发布前全量验证。全量通过后才按人工清单执行 Windows/macOS 真机验收。
- 新变更必须自行验证并记录当次结果，不继承历史绿色结果；归档中旧日期的结果（含旧失败集合）不再代表当前代码状态。
