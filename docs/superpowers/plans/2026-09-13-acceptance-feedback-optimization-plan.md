## 1. 结论摘要

本轮不是若干独立的 CSS 微调，而是六个相互关联的工作包：

1. **全局壳层和反馈系统**：统一顶部工具条、返回/前进、页面居上、滚动所有权、侧栏折叠按钮、全局通知中心和减少动效。
2. **初始化、重新发现和导入状态机**：后台扫描应立即退出初始化；“已选来源”和“扫描候选”必须分层；重复导入必须稳定产生可解释冲突。
3. **LLM 配置与 AI 可用性**：预设选择、协议格式、真实连接、可读数据范围、错误本地化和 AI 搜索前置检查形成闭环。
4. **技能库工作台重构**：重排搜索/筛选/视图/组合工具；修复滚动、分页、偏好降级、通知、批量确认、别名和用途展示。
5. **发现页与品牌资产**：把本地发现主操作前置；接入 SkillHub 应用图标；为 Pi/DeepSeek Harness 增加有来源、可分发的品牌资产或诚实回退。
6. **集成与证据闭环**：统一测试矩阵、独立审查、四份当前开发文档、旧快照归档、提交和推送。

重复反馈要在共享根因处关闭：M-03、M-10、M-17、M-20 和新增02共同归入壳层/页面节奏；新增01与 M-21 的通知问题共同归入全局通知；M-13、M-16、M-05共同归入 LLM/AI 状态闭环。

## 3. 不可破坏边界

- 不删除、覆盖或提交用户真实 Skill、真实密钥、个人目录、缓存、构建产物和未归属改动。
- 当前工作区已有未提交的 Bootstrap/AI 导入预检恢复阻塞修复和开发文档更新。实施主 Agent 必须先审查、复跑其既有测试、记录归属并形成独立前置提交；不得 reset、丢弃或与本轮大改混成一个提交。
- 原文件保护、确定性安全检查先于 AI、网络默认关闭、凭据只进系统凭据存储、搜索候选不自动变上游等边界不变。
- 不增加新依赖来实现简单图标、通知或动画；若确有必要必须先证明现有 React/CSS/motion 无法满足并取得用户许可。
- 9 个主题的名称、顺序、持久化和明暗映射不变；所有新 UI 用语义 token。
- 自动化只证明代码行为；真实系统缩放、系统凭据、真实 API、安装/卸载、链接/联接和 macOS 仍由下一轮人工验收确认。
- 验收清单中 Typora 的个人绝对路径和含个人目录的截图不得进入推送提交。最终当前文档只保留匿名问题摘要、可复测步骤和仓库内相对证据；原始本地证据如需追溯只在本机保存。

## 4. 必用 Skill 与工作方法

Goal 主 Agent：

- `superpowers:subagent-driven-development` 或 `subagent-driven-development`：建立任务账本、独立 worktree、实现→审查→修复循环。
- `systematic-debugging`：M-31、M-13、M-14、M-21 偏好加载等缺陷先定位根因。
- `tdd`：所有行为变化逐个 red→green；测试接缝须先写入任务 brief。
- `finesse-ui`：本项目属于 product/workflow UI，使用 product register、低 spectacle、高 density；壳层、设置、导入、技能库和通知分别读取适用 reference。
- `frontend-design`：确保整体层级、控件一致性和非模板化观感。
- `vercel-react-best-practices`：只采用适用于 Vite/React 的请求瀑布、重渲染、列表和 bundle 规则；跳过 Next.js/RSC/SSR 专属项。

每个实施子 Agent 至少使用 `tdd`、`systematic-debugging`（遇到缺陷时）、`vercel-react-best-practices`；任何修改 UI 的子 Agent还必须使用 `finesse-ui` 和 `frontend-design`。子 Agent 必须在报告中写明读取的 skill、采用的规则、跳过的不适用规则和证据，不能只写“已使用”。审查 Agent也要读取两项 UI skill，但只报告，不混合实施。

## 5. 测试接缝

- **组件接缝**：Testing Library 通过 role、accessible name、状态、焦点、键盘和用户事件验证。
- **流程接缝**：公开 Facade/IPC 契约＋DEV-only preview＋Playwright；禁止用私有状态或 CSS 文本正则代替行为。
- **布局接缝**：800×600、800×900、1024×900、1280×900、1440×900、宽屏全屏；验证内容顶部坐标、单一滚动所有者、末列/底部动作可达和无重叠。
- **通知接缝**：全局跨路由存活、2 秒计时、进入/退出、历史/未读/筛选/清空、聚焦恢复、减少动效、批量详情。
- **导入接缝**：来源选择、来源列表、扫描、候选、冲突和提交分别建模；成功、失败、取消、重复、恢复、权限受限逐态覆盖。
- **LLM 接缝**：各协议使用本地 scripted server/mocks 校验 URL、header、payload、模型列表和错误 presenter；真实 key 不进自动化。
- **资产接缝**：图标路径、尺寸、alpha、Tauri 配置、构建产物和品牌 fallback 可确定性检查。

## 6. 并行实施波次

并发上限按“主 Agent＋3 个子 Agent”。所有子任务使用独立 `codex/` 分支和 worktree；共享文件只由主 Agent/集成 Agent串行修改。

### Wave 0：基线与任务账本（主 Agent）

1. 阅读 AGENTS/README/四份当前文档/本计划，审计当前分支、远端、worktree 和未提交修改。
2. 验证当前未提交恢复阻塞修复；若通过，形成英文动词开头的独立前置提交并推送当前安全分支；若失败，用系统调试修复后再提交。
3. 新建并推送 `codex/acceptance-optimization-2026-09-13`，记录 merge-base。
4. 运行全量基线；失败必须归因，能并行的任务继续，不因单项失败停止整个 Goal。
5. 创建任务账本，写明每个 worktree、文件所有权、基线、依赖、提交和审查状态。

### Wave 1：三路并行

- **T1 壳层/通知/减少动效（UI 子 Agent）**：AppShell、Sidebar、PageFrame/PageHeader、公共 Notification、通用设置开关、基础 CSS 和相关测试。独占 `app/**`、`ui/**`、经分配的 `styles/base.css` 区段。先交付统一契约，其他任务只消费。
- **T2 初始化/重新发现（流程子 Agent）**：M-31、M-25；仅 `features/onboarding/**`、必要的 bootstrap 展示层与专属 CSS/测试。涉及后端状态契约时先报告，由主 Agent分配专属后端子任务或串行处理。
- **T3 LLM/AI 闭环（全栈子 Agent）**：M-05、M-13、M-16；独占 LLM domain/adapter/application 流、settings LLM 展示和协议测试。生成绑定只能用生成器，由主 Agent集成。

Wave 1 集成后跑壳层、settings、onboarding、llm 定向测试、E2E、check/build 和 Rust 相关测试，再独立审查。开放问题返回原实现 Agent 修复并复审。

### Wave 2：三路并行

- **T4 导入与冲突（全栈子 Agent）**：M-29、M-14及导入通知接入；`features/import/**`、duplicate/import application/core/adapter 流和相关测试。不得改共享 UI。
- **T5 技能库工作台（UI 子 Agent）**：M-21、M-22、M-26 回归；`features/skills/**` 和专属 CSS/测试。使用已冻结的全局通知 API和底部 Drawer。
- **T6 发现与品牌（UI/资产子 Agent）**：M-18、新增03、M-30；`features/discovery/**`、Agent 品牌映射、受控 asset 目录、Tauri 图标配置和资产测试。网络检索必须使用官方一手来源并记录许可。

Wave 2 集成后跑 import/library/discovery/brand E2E、300 Skill 性能用例、Rust import/duplicate/LLM 全量、check/build，再独立审查和修复。

### Wave 3：主 Agent 全局接线与逐页回归

1. 串行接入全局翻译、路由、生成绑定和通知事件；避免三个任务同时修改共享文件。
2. 对概览、发现、待处理、设置、详情、项目、Markdown、部署/移除和操作记录逐页审计顶部对齐、返回、通知和滚动。
3. 新增缺失的 E2E/preview 状态；只做本计划范围的修复。
4. 用独立审查 Agent做全分支代码/产品/UI/安全审查；一轮统一修复后做 scoped re-review。

### Wave 4：自动化、文档、归档、提交与推送

1. 运行第 7 节全部命令，失败即修复并重跑相关及全量检查。
2. 将当前四份开发文档形成同一日期的新快照；先吸收用户验收反馈、现有 2026-09-11/10 文档和本轮验证结论，再把旧当前文件移入 `docs/development/archive/2026-09-13-验收反馈优化前/`。`docs/development/` 根目录最终仍只有四份唯一当前文档。
3. 新人工验收清单只保留下一轮需要用户执行的真实桌面/系统/服务项目；已由自动化关闭的问题记录为“待人工复验”，不能写“已真机通过”；发布期 M-01/M-07/M-09等保留。
4. 清理文档中的个人绝对路径、真实密钥、真实 Skill 内容和不可提交截图引用；不删除用户本地证据。
5. `git diff --check`、状态/范围/敏感信息审计；按工作包形成清晰提交，最后提交文档快照。
6. 推送 Goal 分支并核对远端 HEAD。报告提交范围、测试、未解决项和下一轮人工验收入口。

## 8. 完成定义

只有以下全部满足，Goal 才能 `complete`：

- T1～T6、全局接线、独立审查和修复全部完成并合入 Goal 分支。
- 用户已反馈的新增01～03、M-03/M-05/M-10/M-13/M-14/M-16/M-17/M-18/M-20/M-21/M-25/M-29/M-30，以及 M-31 的可自动化部分均有失败测试、根因、实现和绿灯证据。
- M-27 已通过行为和所有未执行功能无回归。
- 必跑验证全部通过；不存在被隐藏、降低或删除的断言。
- 四份当前开发文档同步，过期当前文档已归档，个人信息未推送。
- 工作区无本 Goal 遗留改动，分支提交完整并成功推送，远端 HEAD 已核对。
- 剩余事项只允许是明确列出的下一轮人工验收/发布期真机验收；不能把可自动化问题转嫁给用户。

执行过程中不要因阶段性测试完成、上下文压缩或单个子任务完成而停下。只有需要新的用户授权、不可获得的真实凭据/设备、外部服务持续不可用或存在无法安全合并的他人改动时才可报告阻塞；遇到局部阻塞要继续推进不依赖部分。达到上述终点前不得标记 Goal 完成。
