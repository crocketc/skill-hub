## 2. 分波实施

三波按体量与依赖排序；同波内各项相互独立、可并行派发。每项均走 TDD（先写失败测试，再最小实现，后重构），前后端分 A/B 执行代理或由主代理直接接线（届时按团队规则 Luna/max）。

### Wave 1（小体量，先行）

#### W1-1 跟进 5：备份不含草稿的明确说明（极小）

- 行为：备份完成页与备份说明区新增一行提示"未保存的编辑草稿不在备份内，请先保存"（中英 i18n）。后端备份范围不改（已不含 drafts）。
- TDD：`DataProtectionPage.test.tsx` RED——完成页与说明区各断言提示文案存在；GREEN——文案接入（含 i18n 键、中英等长）。
- 判据：完成备份后能看到提示；说明区静态可见；不改变备份内容与恢复行为。

#### W1-2 跟进 4：删除主体级联清理编辑草稿

- 行为：删除（含批量删除）主体时一并删除 `root/drafts` 下该主体的全部编辑草稿；删除影响清单列出"未完成的编辑草稿"，确认文案说明"将同时删除未完成的编辑草稿"；一次确认完成。
- TDD：后端 RED——removal_service 删除含草稿主体后草稿文件不存在、其他主体草稿不受影响；删除失败时草稿与主体同命运（不产生孤儿草稿）。前端 RED——影响清单含草稿条目且确认文案含说明。
- 判据：删除后无孤儿草稿；确认框说明可见；批删除同样级联；既有"不丢用户原文件"边界以"草稿属主体私有数据、随主体删除"为已裁决例外。

#### W1-3 FB-006：导入检查结果登记为该版本首次基础检查记录

- 行为：导入边界扫描结果保存并绑定导入内容版本，标注来源"导入时检查"；导入后列表/详情/安全页显示真实状态，重启保留。升级前旧导入缺记录的如实显示缺记录并引导重查，不伪造历史通过；同版本不覆盖已有更新结果；持久化失败不假通过（导入整体失败）。
- TDD：后端 RED——①导入成功后该内容版本存在基础检查记录且来源标注"导入时检查"；②facade 重开后记录仍在；③同版本已有更新记录时不覆盖；④检查记录写入失败时导入返回失败、不留"看似成功"的库状态。前端按既有检查链路消费，必要时补状态断言。
- 判据：导入完成即显示真实检查状态；旧导入缺记录引导重查；重启保留。

### Wave 2（中体量）

#### W2-1 跟进 6：来源更新守卫式快速重试

- 行为：来源更新执行失败后，失败记录保留用户决定；重试前重核事实（本地当前内容、上游内容与原预览一致）：一致则按原决定直接重试、免重新预览；不一致（上游更新、本地改动）落回重新预览再确认。重核通过等价于原预览的事实保证。
- TDD：后端 RED——①失败后以原 preview_id+原决定重试，事实一致则成功且不再要求预览；②上游内容变化 → 拒绝并要求重新预览；③本地内容变化 → 同；④重试成功后原决定消费语义与首次一致。前端——失败结果提供"按原决定重试"入口并展示失败原因；重核不一致时引导重新预览。
- 判据：失败恢复少一步且不掩盖事实变化；三条不一致路径全部落回重新预览。

#### W2-2 FB-007：批内冲突分组与显式处置（第一期）

- 行为：冲突分析新增"批内"分组：同内容同来源（明显重复）建议合并为一个、其余跳过；同名不同内容要求用户逐个显式处置（独立命名或跳过），不给静默默认、无处置则提交被拒；提交期库或文件再变化则重新确认。第一期先做分组呈现＋同名显式处置，逐个重命名体验后补。
- TDD：后端 RED——①批内同内容同来源 → 分析产出合并建议＋跳过其余；②批内同名不同内容 → 未显式处置时提交被拒，处置（独立命名/跳过）后按处置执行；③提交期文件变化 → 既有预览绑定失效路径重新确认。前端——ConflictResolution 新增"批内"分组与逐项处置控件。
- 判据：批内重复不再静默改名复制；同名不同内容必有用户决定；库内冲突呈现不受影响。

### Wave 3（大体量，最后实施）

#### W3-1 FB-003：安全三级分级＋预警状态（修订后裁决）

裁决要点（2026-10-05 修订）：三级分级，**无任何一级无条件硬拦**；危险级导入时展示具体风险明细、用户显式决策继续/取消，继续导入后进入预警状态；警告级导入后进入预警状态；预警=不可派发+加入待办+三选处理（信任解除／不信任删除／稍后处理持续不可派发）；预警与信任绑定内容版本（同版本不重复提示，版本变化重新提示）；分级只基于确定性规则，AI 仅辅助解释、不参与判定；伴生修复：明细完整展示、内部编号不外露、误报回归素材。

实施拆分（每步独立 RED→GREEN，顺序依赖）：

1. **分级规则表**：`security/rules.rs` 现有规则集划分三级（危险/警告/放行），确定性规则、逐条注明分级依据；`BasicScanReport` 携带分级结果。
2. **导入流改造**：`enforce_import_security_gate` 不再对任何 finding 直接抛错：放行级直接过；危险/警告级返回结构化分级报告，前端展示完整明细（file/line/说明、可读名称不外露内部编号），危险级需显式"继续导入/取消"，警告级可直接继续但提示导入后预警。
3. **预警状态落地**：catalog 记录预警状态并绑定内容版本；`deployment_service` 派发前拦截预警主体（不可派发的确定性行为）；`pending/` 派生待办条目。
4. **三选处理动作**：信任（解除预警、恢复可派发）、不信任（删除主体）、稍后处理（留待办、持续不可派发）；三个动作均记录决定与版本。
5. **前端呈现**：导入向导风险明细与决策步骤；列表/详情预警标识（可读说明，不只靠颜色）；安全页与待办的处理入口。
6. **伴生修复**：明细完整展示不丢弃；内部编号不外露；建立误报回归素材目录（真实误报样本固化为测试素材，不含用户真实数据）。
7. **AI 边界测试**：断言分级与放行判定不依赖 AI 结果；AI 解释仅作辅助展示（既有 `facade_import_ai_checks.rs` 语义保持隔离）。

判据：任何 finding 都不再无条件堵死导入；危险级继续导入后不可派发且待办可见；信任后可派发；版本内容变化重新进入预警；同版本不重复提示；三个处理动作全链路生效；明细完整、无内部编号外露。

## 4. 验证策略

- **每项**：TDD 定向测试（改动 crate 的 `cargo test --test <file>` + `apps/desktop` 下定向 vitest）；行为变更不改既有断言语义，不删除测试。
- **每波整合后**：定向全量（受影响 crate + 受影响 vitest 文件）+ **workspace clippy `--all-targets --all-features -- -D warnings`**（K10 教训：clippy 不在定向测试覆盖内，每波必跑）+ `git diff --check` + i18n 中英键数一致。
- **E2E**：受影响 spec 定向（import/removal/backup/security/source 相关）；三波全部完成后在最终整合提交上跑全量 E2E。
- **生成绑定**：W3-1 涉及 wire 契约变化时由生成工具更新（`SKILLHUB_WRITE_BINDINGS=1` 临时变量流程），不手写 bindings.ts。
- **发布前**：最终整合提交上执行 `pnpm ci:local` 十项、`pnpm verify:release`、`pnpm test:release`、全量 E2E、原子测试目录校验与 `git diff --check`，记录结果并处理失败。
- **人工验收清单**：每波完成后在[人工验收清单](../../development/人工验收清单-2026-10-05.md)补充对应流程判据（流程 C/F 导入链路补分级决策与预警、删除流程补草稿级联与确认文案、备份流程补提示文案、来源更新流程补快速重试），仍按完整操作流程编排，不逐条罗列。

## 5. 顺序、依赖与风险

- Wave 1 三项相互独立，可立即并行；Wave 2 两项相互独立，可在 Wave 1 后或并行（无代码依赖）；**Wave 3 最后**——依赖 W1-3 建立的"检查记录绑定内容版本"机制（预警状态同用版本绑定），且门禁语义变化最大，规范收口先行。
- 风险与边界：
  - W3-1 改变安全门禁语义（拦 → 用户决策），是本轮最大的行为变化；实施前必须完成产品规范收口，避免代码先行。
  - 预警状态新增涉及 catalog 模型、派发门禁与生成绑定，影响面跨 core/application/desktop，需按共享契约单一写入者协作。
  - W1-2 删除级联是"不丢用户文件"边界的已裁决例外（草稿随主体删除），实施与文档表述都要明确这一点，避免被误读为数据丢失缺陷。
  - 全部波次不阻塞当前真机人工验收；人工验收反馈的相关现象按流程登记，作为实施的实例素材。
