# 未决事项裁决建议（2026-10-05）

> 状态：**待用户裁决**。本文整理 v0.2.0 当前六项未决事项的背景、选项与建议，作为裁决输入；结论经用户确认后写入对应产品规范（导入与安全、检查与记录、备份等），并排入实施计划，本文届时在"裁决"栏标注结论。六项均不阻塞正在进行的真机人工验收。

## 一、用户反馈过的问题（FB，这轮未修）

### 1. FB-003：导入安全检查"一刀切"，拦截过多且说明不足

**用户场景与现状**
导入一个 Skill 时应用先做安全扫描。目前只要扫出任何一条可疑内容，无论轻重，整个导入直接拦截，无法继续。用户反馈"大量安全拦截"，其中预计存在误报（如普通教程文本同时出现"下载"与"执行"字样被当危险）。另有三个伴生毛病：警告级问题也整体拦截（无分级）；部分扫出的明细未完整展示（丢弃）；界面偶尔露出 `candidate-37f2` 式内部编号而非可读名称。

**为什么留待裁决**
"什么必须拦、什么只警告、什么直接放行"是安全门禁的产品标准，至今没有定论；标准不定，实现就是瞎猜。这轮实施计划明确"不擅改门禁"。

**裁决点：采用哪套分级标准？警告级放行后如何记录？**

| 选项 | 内容 | 后果与代价 |
| --- | --- | --- |
| A（建议） | 三级分级：确定性危险（真实密钥、明显恶意命令、路径穿越）→ 阻断；可疑但常见模式（教程提及危险操作）→ 警告，用户显式确认"仍要导入"后放行并记录该决定；其余 → 放行。同版本不再重复警告，新版本（内容变化）重新警告。分级只基于确定性规则，AI 仅辅助解释不参与放行 | 误报不再堵死导入；用户保留知情权与决定权；需要设计分级规则表与误报回归素材，工作量最大 |
| B | 两级：仅确定性危险阻断，其余全部放行并在详情可见 | 实现最简；但把全部判断责任推给用户，"警告"信息容易被忽略 |
| C | 维持全阻断，只补全明细展示与可读命名 | 不解决"误报堵死导入"这一用户主诉，不建议单独采用 |

**无论选哪项都一并修复（无需裁决）**：明细完整展示不丢弃；内部编号不外露；用误报素材建立回归样本。

**建议**：A。理由：与"必要决策不能批量忽略、一次操作汇总必要确认"的既有模型一致；警告级记录决定（类似来源忽略候选的先例）避免重复打扰。

**裁决**：（待填）

### 2. FB-006：导入完成后检查显示"未运行"

**用户场景与现状**
导入时应用其实已做过一次基础安全检查，但结果没有与导入的内容版本绑定保存。用户导入完打开列表／详情／安全页，看到"未运行"，好像从未检查过，必须手动再点一次。用户已反馈此现象。

**为什么留待裁决**
修复牵扯"导入时的扫描结果算不算一次正式检查记录"的产品口径：算，则导入行为语义变化（导入即有记录）；不算，则导入后应自动补查。

**裁决点：导入时的检查结果要不要作为该版本的正式检查记录？**

| 选项 | 内容 | 后果与代价 |
| --- | --- | --- |
| A（建议） | 保存并绑定版本：导入扫描结果登记为该内容版本的首次基础检查记录，标注来源"导入时检查"；详情／列表显示真实状态。升级前导入的旧技能缺记录的不伪造，如实显示缺记录并引导重查 | 用户看到真实状态，消除"明明查过却说未运行"；需处理记录来源标注、同版本不覆盖更新结果、持久化失败不假通过三个细节；工作量小、独立性强 |
| B | 不保存，导入完成后自动触发一次正式重查 | 复用现有检查链路、改动更小；但重复扫描一次、完成后短暂"检查中"状态；导入与检查耦合更深 |
| C | 维持现状 | 用户主诉未解决，不建议 |

**建议**：A。理由：诚实呈现原则的直接落实；B 的自动重查在离线／权限受限场景反而制造新的失败路径。

**裁决**：（待填）

### 3. FB-007：批量导入时批内同名／重复不提示

**用户场景与现状**
一次批量导入多个 Skill 时，冲突预览只对比"这批 vs 库里已有"，不对比"这批内部彼此"。批内两个同名 Skill 在提交前完全无提示，提交时其一可能被静默改名复制。用户已反馈"出现多个同名技能且无提示"。

**为什么留待裁决**
批内冲突的默认处置策略（合并、跳过、独立命名）是产品行为，不是纯技术修复；不同策略对应不同的确认负担。

**裁决点：批内重复／同名在提交前如何呈现与处置？**

| 选项 | 内容 | 后果与代价 |
| --- | --- | --- |
| A（建议，可分期） | 冲突分析增加"批内"分组：同内容同来源（明显重复）建议合并为一个、其余跳过；同名不同内容要求用户逐个显式处置（独立命名或跳过），不给静默默认；提交期库或文件再变化则重新确认。第一期可先做分组呈现＋同名显式处置，逐个重命名体验后补 | 与"库内冲突"同一套心智；消除静默复制；预览页信息量增加，需控制呈现密度 |
| B | 最小改动：仅提示批内重复，默认合并、允许批量改 | 工作量小；但同名不同内容时默认合并仍有覆盖风险 |
| C | 全部默认独立命名并提示，用户事后再改 | 不丢数据；但产生用户事后要清理的重复项，与"提交前明确呈现"的诉求不符 |

**建议**：A（第一期口径）。理由：同名不同内容属于必要决策，不能静默默认。

## 二、本轮开发后新发现的边界（未裁决，不影响验收）

### 4. 删除 Skill 时，未完成的编辑草稿会残留

**用户场景**：编辑正文改到一半关闭（草稿已自动保存）→ 之后删除该 Skill → 草稿成为无人关联的残留数据。不丢内容、不可再访问，仅残留。

**裁决点：删除主体时草稿是否一并清理？**

| 选项 | 内容 | 后果与代价 |
| --- | --- | --- |
| A（建议） | 级联清理：删除确认中说明"将同时删除未完成的编辑草稿"，一次确认完成 | 符合"一次影响确认"模型；草稿属主体私有数据，保留只会成为永久残留；工作量小 |
| B | 保留草稿并提供孤儿草稿清理入口 | 需新增一个管理入口，价值低 |
| C | 维持现状 | 残留累积，不建议 |

**裁决**：（待填）

### 5. 备份／恢复不包含"编辑中的草稿"

**用户场景**：编辑到一半 → 做备份 → 之后恢复备份：库完整恢复，但未定稿的草稿丢失（已保存内容均安全）。

**裁决点：草稿是否纳入备份范围？**

| 选项 | 内容 | 后果与代价 |
| --- | --- | --- |
| B（建议先行） | 暂不纳入，但在备份完成页与备份说明中明确一行"未保存的编辑草稿不在备份内，请先保存" | 一行说明即可消除意外感，成本极低 |
| A | 草稿纳入备份与恢复 | 恢复出的旧草稿可能与恢复后的库版本不匹配，需处理冲突；草稿属临时数据，收益有限；列为后续增强 |
| C | 维持现状且不说明 | 用户无知情渠道，不建议 |

**建议**：先 B，A 作为后续增强按需排期。

### 6. 来源更新：预览确认后执行失败，重试需重新预览

**用户场景**：上游有更新 → 应用给出更新预览（哪些文件会变）→ 用户确认采纳 → 执行中途失败（如文件被占用）→ 重试时不能沿用原预览，必须重新生成并再确认一次。多这一步是刻意的：失败后磁盘事实可能已变，旧预览可能失真。

**裁决点：要不要为"校验已通过、执行失败"场景提供免预览的重试通道？**

| 选项 | 内容 | 后果与代价 |
| --- | --- | --- |
| B（建议） | 守卫式快速重试：失败记录中保留用户决定；重试前先重核事实（本地当前内容、上游内容与预览时一致），一致则按原决定直接重试，不一致则落回重新预览 | 与"预览与当时事实绑定"的机制同源——重核通过等价于预览保证；失败恢复少一步；需实现重核比对，工作量中等 |
| A | 维持现状：失败后一律重新预览 | 最简单、最保守；多次失败时体验繁琐 |
| C | 失败自动重试若干次 | 掩盖失败原因，违背诚实呈现，不建议 |
