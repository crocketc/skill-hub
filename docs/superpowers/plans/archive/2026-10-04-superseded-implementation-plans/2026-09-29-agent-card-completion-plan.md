## 实施顺序与可并行范围

1. **DEV-103 已收口提交**：待建选择、只读扫描和能力图标提交于 `6bed5cef`，自动化验证通过；保留 `.playwright-cli/` 本机资料。
2. **先固化事实（DEV-104、DEV-107）**：Rust 先写失败测试，再最小修正投影与异常观察；生成工具更新绑定。两个任务修改发现契约和应用门面时应串行，避免同文件冲突。
3. **再迁移消费点（DEV-105、DEV-106）**：基于已固定契约分独立文件集合推进。详情/自定义与部署/项目可用独立 worktree 并行；合并后用同一快照核对成员 ID、能力和选择展开。
4. **最后收视觉（DEV-108，含 DEV-102）**：先加载 `frontend-design` 与 React 最佳实践；写布局/多 Logo/无障碍失败用例后改共享组件和局部 CSS。待卡片数据结构稳定后进行，避免视觉测试反复改动。
5. **整体验证与交接（DEV-109）**：运行相关 Rust/前端测试、格式/静态/类型/构建和浏览器 E2E；先交付代码与自动化结果。Windows/macOS 流程 L 按用户要求暂缓，待用户恢复验收时再构建对应 release 并分别取证。并行 worktree 完成后确认无未提交或未合并内容，再归档多余 worktree。

各 Task 只修改直接相关的代码和测试；不升级依赖、不改数据库实体身份或已有安全授权边界。每个阶段先写失败测试，完成后更新开发状态、自动化说明和验收矩阵；人工结果仅在真实桌面执行后写入验收清单。
