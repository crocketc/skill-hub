# 集中库初始化与生命周期设计

日期：2026-09-10
状态：待评审

## 1. 背景与问题

当前桌面端在启动时构造 `LocalApplicationFacade`，并把集中库路径复制到 `VersionStore`、部署、移除、对账等多个服务中。初始化向导虽然可以把新路径写入数据库，但无法同步替换这些已构造组件持有的路径，因此只能尝试通过重启重新装配运行时。

该方案存在两个问题：

- 初始化是否成功依赖桌面进程能否自行重启，源码开发环境下表现不稳定。
- “重新运行初始化向导”复用了首次初始化界面，允许用户再次选择集中库，但后端又禁止已初始化实例修改库根，产品流程与系统约束冲突。

本设计取消“保存后重启”的依赖，把首次初始化、重新发现扫描和未来的集中库迁移拆成三个明确的生命周期流程。

## 2. 目标与非目标

### 2.1 目标

- 首次初始化选择集中库后，无需重启即可进入下一步并继续使用该路径。
- 集中库路径在一次应用生命周期内只有一个受控激活点，避免不同组件使用不同路径。
- 已完成初始化后，重新运行发现与扫描不能修改集中库。
- 首次从备份恢复时，先明确恢复目标集中库，再执行恢复。
- 所有失败路径保持数据库状态与内存运行时一致，并提供可重试的明确错误。

### 2.2 非目标

- 0.2.0 不提供已初始化集中库的迁移、移动或切换。
- 不在运行中的普通业务操作之间动态切换集中库。
- 不改变应用更新完成后的必要重启行为。
- 不改变 CLI 显式传入数据库和集中库路径的启动方式。

## 3. 生命周期模型

集中库运行时使用两个状态：

- `Pending`：应用尚未完成首次初始化，集中库尚未激活。
- `Active { root, store }`：集中库路径及其 `VersionStore` 已作为一个不可分割的上下文激活。

状态转换仅允许：

```text
Pending --首次初始化激活--> Active
```

应用启动时如果数据库已有有效集中库路径，则直接以 `Active` 状态构造。初始化完成后不允许再通过初始化接口改变路径；未来如需迁移，应由独立迁移流程完成。

## 4. 后端设计

### 4.1 共享集中库上下文

在 `LocalApplicationFacade` 内引入受控共享的 `LibraryRuntime`（或同等职责的类型），由所有依赖集中库的服务共同引用。它持有 `Pending` 或 `Active` 状态，可使用 `Arc<RwLock<...>>` 等方式实现，但不得向业务层暴露可任意写入的裸路径。

部署、移除、对账、扫描及其他集中库操作不再在构造时各自复制 `library_root`。每次业务操作开始时，从 `LibraryRuntime` 获取一次不可变的 `Active` 快照，并在该次操作中持续使用同一快照，避免执行过程中读到不一致状态。

更新器、外部链接、凭据、网络客户端和路径授权等非集中库依赖保持现有实例，不通过重建整个 facade 来切换路径。

### 4.2 首次激活事务

首次选择集中库时执行以下顺序：

1. 获取激活互斥锁，串行化并发提交。
2. 确认应用尚未完成初始化，且运行时仍为 `Pending`。
3. 规范化并校验候选路径，包括目录边界、可访问性和写入能力。
4. 根据“新建”或“使用已有”模式初始化或验证集中库；不得覆盖已有用户文件。
5. 用候选路径构造完整的 `VersionStore` 和集中库上下文。
6. 在数据库事务中持久化集中库路径。
7. 发布已经构造成功的 `Active` 上下文。
8. 返回成功，前端直接进入下一步。

第 7 步应设计为在数据库提交后不再执行可失败的 I/O。任何前置步骤失败时，不更新数据库，也不发布运行时。若新建目录时已经写入了安全的集中库元数据，可作为重试产物保留，但不得删除或覆盖用户原文件。

### 4.3 访问约束与错误

- `Pending` 状态下调用依赖集中库的业务命令，返回稳定的“集中库尚未就绪”错误。
- 已完成初始化后再次调用激活接口，返回稳定的“集中库路径已锁定”错误。
- 已有集中库需要验证清单格式、版本兼容性和写入权限，并返回可操作的错误信息。
- 并发激活请求必须串行执行；第一个成功后，后续请求按已激活或已锁定处理。
- 不允许出现数据库指向新路径、内存组件仍使用旧路径的分裂状态。

## 5. 前端流程设计

前端根据初始化状态进入不同模式，不再让同一路由无条件展示同一套分支选择。

### 5.1 首次初始化模式

适用条件：`initialization_state === "not_initialized"`。

用户可以选择：

- 新建集中库：选择空目录或可安全初始化的目录，激活成功后进入兼容目标发现步骤。
- 使用已有集中库：选择有效集中库，验证并激活成功后进入下一步。
- 从备份恢复：先选择并激活恢复目标集中库，再选择备份并执行准备、确认和恢复。

集中库步骤的主按钮改为“保存并继续”。成功后不调用重启命令，也不显示“即将重启”。失败时停留在当前步骤，保留可重试输入并显示明确原因。

从备份恢复失败时仍处于首次初始化流程，用户可以重试备份、重新选择目标，且不得影响其他目录。

### 5.2 重新发现与扫描模式

适用条件：应用已初始化，用户从设置页或直接访问初始化路由进入。

设置入口名称改为“重新发现 Agent 与 Skill”。该模式：

- 只读显示当前集中库路径。
- 不显示“新建集中库”“使用已有集中库”“从备份恢复”分支。
- 不显示路径选择器，也不调用集中库激活接口。
- 只执行兼容目标发现和 Skill 扫描。
- 取消时返回设置页，完成时返回主界面。
- 失败时不修改集中库、初始化状态和已有数据。

重新扫描的完成状态与首次初始化的 `onboarding_skipped` 等标记分开处理，不能因再次扫描覆盖用户首次初始化时的选择记录。

### 5.3 集中库迁移模式

集中库迁移是独立设置能力，不复用初始化向导。0.2.0 继续明确显示“暂不可用”或不提供入口。后续实现时必须单独设计停写、复制或移动、校验、切换及回滚流程。

## 6. 其他流程边界

- 数据保护页的备份与恢复始终作用于当前已激活集中库，不切换库根。
- 首次初始化中的备份恢复必须显式选择目标集中库，不能隐式使用应用启动时的默认路径。
- CLI 使用显式参数启动时直接构造 `Active` 上下文，并复用相同的路径校验规则。
- 应用更新完成后的重启属于版本更新流程，继续保留，不受本设计影响。
- 开发预览和测试夹具使用固定测试上下文，不依赖真实用户集中库。

## 7. 命令与兼容性调整

- 将现有 `set_library_root` 的职责收敛为首次激活集中库，接口名可保留以减少绑定变更，也可重命名为更明确的 `activate_library_root`；无论命名如何，都必须遵守生命周期约束。
- 删除初始化向导对 `restart_application` 的调用及为该流程添加的重启适配代码和测试。
- 若 `restart_application` 没有其他合法调用方，则删除该命令；应用更新使用自身独立的重启路径。
- 前端路由可继续使用 `/initialize`，但必须根据后端初始化快照明确选择首次初始化或重新扫描模式。

## 8. 验证方案

### 8.1 Rust 测试

- 有效新目录可使运行时从 `Pending` 转为 `Active`，所有依赖服务使用所选路径。
- 有效已有集中库可通过验证并激活。
- 非法路径、只读目录、不兼容清单和初始化失败均不持久化、不发布新状态。
- 初始化完成后禁止再次激活其他路径。
- 并发激活被串行化，不能产生双重激活或状态分裂。
- 首次恢复使用用户选择的目标路径，恢复失败后仍可安全重试。
- CLI 显式路径启动后直接处于 `Active`。

### 8.2 前端测试

- 首次初始化显示三个分支，成功后“保存并继续”，且不调用重启。
- 已初始化后进入重新扫描模式，不显示分支和路径修改控件。
- 重新扫描的取消、失败和成功跳转符合约定，且不改首次初始化记录。
- 首次恢复必须先选择目标集中库。

### 8.3 端到端与人工验收

- 首次启动选择自定义集中库后，无需重启即可进入下一步并完成初始化。
- 设置页进入“重新发现 Agent 与 Skill”后，只能扫描，不能改变集中库。
- 已初始化实例无法通过直接路由或后端调用切换集中库。
- 从备份恢复可明确看到目标路径，并验证失败重试路径。
- 原 TC-US001-M02 的失败记录保留，修复后按新流程重新验收。

## 10. 完成判定

只有满足以下条件才可认为本问题解决：

- 首次选择集中库后无需重启即可继续。
- 运行时所有集中库依赖使用同一个已激活上下文。
- 已初始化后的重新扫描不提供集中库修改入口。
- 失败和并发场景不存在数据库与运行时分裂。
- 自动化测试通过，四份当前开发文档同步，TC-US001-M02 在真实桌面环境复测通过。
