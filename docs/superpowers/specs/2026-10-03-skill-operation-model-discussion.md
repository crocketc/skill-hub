# 单技能操作模型讨论与归档功能移除裁决（2026-10-03）

## 1. 状态与依据

用户要求共同梳理单技能可执行操作，用统一模型设计抽屉、详情、列表及批量按钮，并由每个动作调用相应已有流程模块。操作目录和新增批量支持仍在讨论，不据此一次性扩展新功能或创建通用流程引擎。最新边界修正见第15节：Skill主体操作与已有关系治理分别建模，跨模块入口只调用权威流程；第14节是跨流程调用表，不能整体当成Skill自身动作集合或另建关系状态。

**已裁决：删除 Skill 的归档功能，不保留 Skill 归档专属状态/数据。** 此授权更新并替代此前“暂不列常用动作、保留归档兼容”的建议。产品负责人决定已有归档 Skill 迁回常规状态并清理归档专属偏好/条件，主体、内容、版本和实际使用关系不因这次功能移除被删除。涉及真实用户库的迁移由经过测试的应用升级路径执行，开发不得直接清理用户库。

本裁决只针对 Skill 生命周期中的归档。关系明确结束后的历史、回滚恢复依据、文档历史目录，以及 ZIP 导入/导出不属于本次移除范围；不能全文替换 archive 字样破坏这些能力。现有 Deprecated 精确后端语义先核查，不能继续被前端笼统当作归档，也不能未经核查顺带删除其他生命周期能力。

**已裁决：保留试用与到期复核。** 期限是主体复核提醒，不是使用关系状态；到期不自动删除、不自动回收链接，也不自动形成归档。归档迁移保留原有 trial_due。用户状态以常规/试用呈现，试用到期是具体提醒；不得把检查结果、上游更新或链接异常混为主体生命周期。到期动作建议转常规、延长试用、删除技能，分别调用元数据/试用或删除确认流程；具体按钮/放弃试用旧路径仍需按整体操作目录确认。

## 2. FB-013：归档功能移除的增量范围

- 前端：删除归档单项/批量动作、筛选项、状态徽标、说明、快捷视图及相关翻译；检查列表/卡片/抽屉/详情/试用/待办等消费点，不留只是藏按钮的旧能力。URL、持久化保存视图和偏好中的旧归档条件去掉，避免空筛选或把全部项目误选成归档集合。
- 后端：移除 SkillLifecycle::Archived 与归档列表过滤及动作分支，生成绑定必须由工具更新；仅为读取旧持久化文件设计的迁移解析可以识别旧值并立即规范化，不能保留可再次执行归档的公开契约。
- 数据：数据库和可携带库元数据中的旧归档状态迁为 Normal；归档专属偏好/属性清理，无需保留归档状态副本。保留 SkillId、版本内容、标签/用途/备注、检查结果和关系身份，不触发派发或回收。迁移幂等、可重启、失败明确；旧备份导入也需规范化，不能恢复失效的归档能力。
- 边界：现有 Normal/Deprecated 的精确含义与试用期限分别核查，不用“所有非Normal都是归档”的旧 mapper；不能用“停用/隐藏”等新动作悄悄重新引入被删的归档功能。是否保留其他生命周期操作由后续模型讨论决定。
- 实施：A 在 R1 小契约交付后安排后端/存储/迁移/生成绑定；B 在原 worktree 中删除前端消费，接真实绑定后核对全域。与 FB-010—012 及 F1/F2 顺序协调，小提交，负责人不写业务代码。
- TDD：旧归档库/portable 元数据/备份读取迁移、无再归档命令、重复启动/中断失败、旧 URL/视图条件清理、批量动作消失、三处状态一致、主体/版本/关系和试用事实未误改。运行相关检查/构建/生成契约测试，真机结果单独记录。

## 4. 每个动作的统一描述（草案）

每个动作至少明确：用户名称与说明、对象范围（主体/具体版本/具体关系/组合）、前置条件与受限原因、单项/批量能力、参数与影响预览、是否确认/可否取消、所属流程、完成判据、需要刷新的查询、失败重试/恢复入口。内部标识只用于执行，不进入可见名称或说明。

用户入口只选择动作和真实对象，再调用已有流程；轻量元数据编辑保存即可，涉及文件/版本/共享/删除的动作进入明确预览与确认。执行后先查真实结果并刷新所有消费面，通知是补充；关闭提示不代表操作或待办完成。

本轮先确认操作模型，再决定抽屉、完整详情及批量入口分工。用户明确内容/版本操作不在抽屉展示；不能在抽屉“更多操作”中绕过这一要求。已经明确授权的抽屉基础/AI检查与翻译/画像入口继续原范围实施，字段编辑用笔形按钮。完整详情应包含抽屉能力，具体新操作布局待模型收口，不把全部候选铺成固定按钮。

## 5. 下一步讨论

归档移除、试用/复核保留已确认。继续确认目录覆盖范围，逐类固定对象、条件、影响和结果，最后确定单项与批量入口；优先梳理“编辑技能画像”和“修改真实内容/版本”的不同影响，以及各自确认/刷新边界。已确认的归档移除和抽屉/安全/通知缺陷按现有授权推进；未确认的操作扩展不提前开发。

## 6. 来源分类与“查找更新来源”（流程已确认，增量实施排队）

用户确认查找更新来源流程，并要求尽量自动化、接入AI辅助检索。本机其他导入路径不属于本次寻找对象。以下查找/验证/确认链路作为已确认范围；具体更新通道、整个操作目录和新增批量支持继续讨论，不据此全量开发。按第6.5节排队，不打断当前关系契约、抽屉与归档任务。

### 6.1 来源用途和来源形态

两种用途分别呈现：**导入记录**说明过去从哪里取得内容，允许多次记录，不随更换上游覆盖；**更新来源**说明当前从哪个网络位置检查后续版本。每个 Skill 明确选定一个更新来源，其他网络记录仍可追溯或作为待选候选。更新来源身份与主体、内容版本、使用关系分别保存。

| 来源形态（用户视角） | 位置示例与定位信息 | 产品职责 |
| --- | --- | --- |
| 本机来源 | 本机目录、Agent/项目目录、共享目录或本机导入包 | 导入追溯；已识别使用目标另走关系治理，不作为本次联网查找/升级上游 |
| 网络／技能集合仓库 | 同仓库包含多个技能，定位仓库、分支/更新通道、具体技能子目录 | 仓库可供发现多个Skill，但每个主体绑定精确技能目录，不能绑定整个集合替换一个技能 |
| 网络／独立技能项目 | 单技能仓库，技能通常位于根目录，也可能在确定子目录 | 和集合仓库复用同一仓库定位模型，根目录为合法明确坐标 |
| 网络／直接下载地址 | 可访问的技能包/文件地址，需验证包结构和实际获取能力 | 可以是导入来源；只有真实支持稳定版本核验与重新取得内容的适配器才作为更新来源，否则明确“仅供导入” |

GitHub 是托管平台，与上述仓库形态分开记录/展示；不把“GitHub”和“仓库”列为互斥同级分类。技能市场/索引页是发现渠道，关联更新时要解析到实际内容来源；无法解析不能把列表页假装成更新上游。网络能力范围遵循当前实际适配器，不承诺支持所有Git平台/网页/下载格式。

集合/独立是用户理解用的展示类型，可由已核验结构推导，结构未知时先显示网络仓库，不能凭名字或链接拼写猜。后端保留既有local/https/git传输类型并增量补足定位及明确选择，不能再建平行来源状态机。

### 6.2 查找、验证、关联、更新的完整链路

1. 技能无更新来源时提供“查找更新来源”，弹窗/独立步骤预填名称，可辅助参考作者、描述及既有网络线索；另提供“粘贴网络地址”。不遍历其他本机目录作为升级候选，不上传原始Skill内容/脚本/凭据进行搜索，AI辅助沿用现有配置和授权边界。
2. 复用现有在线搜索与已登记仓库发现，结果列来源形态、平台/作者、技能位置、用户可读的匹配证据。候选不自动关联，不凭同名宣称同一主体或“官方来源”；没有结果或网络受限说明真实情况。
3. 获取并只读核验选定候选的合法边界、Skill文件及依赖包结构、仓库坐标和可检查更新能力。展示“内容一致／内容不同／尚未核验”等事实，而非虚构可信评分；先完成精确目录选择，再由用户确认这是该主体的更新来源。内容不同可以代表上游新版，不能仅同名自动绑定，也不能仅凭差异自动拒绝所有候选。
4. 确认后只记录更新来源并刷新来源状态；不改当前主体内容、不变更链接、不补造导入历史。来源关联与采用内容是两个独立决定，关联成功后可“检查更新”。坐标或能力不全必须报具体原因，不能显示关联就等于可升级。
5. 检查有更新后进入既有版本流程，明确内容变化和所有跟随当前版本的目标影响；用户确认并通过既有检查/备份/恢复边界后才采用新版本。上游更新待办留在生命周期模块，不进入关系治理。

建议单项入口：未关联→查找更新来源；已关联→检查更新，更多操作中提供更换/解除关联及打开来源页面；来源失效→说明原因、重试或更换。解除关联只停止上游检查，不删除主体、版本、导入记录或使用链接。批量查找可以汇总候选，但每个主体分别确认精确更新位置，不能同名自动批量绑定；新增批量能力仍需后续裁决。

更新位置要记录分支/目录及选定的更新通道，检查与采用必须对同一已核验内容；不自动从不同分支、标签或另一个仓库切换更新。具体“稳定发布/分支”的通道规则继续讨论，不能将“所有链接跟集中库当前版本”误读成“自动升级到远端最新”。

### 6.3 前端及增量锚点

- 来源区分别显示“导入记录”和“更新来源”，网络形态/平台为短徽标，悬浮/聚焦说明意义；主动作随真实来源情况变化，不在抽屉固定区铺满来源按钮。
- 查找、验证、确认采用 bounded 弹窗或独立步骤，结果内部滚动，主抽屉/列表/图谱画布不被挤压；长URL/目录前段省略、完整用户可读提示，原始标识只内部关联。
- 已有基础：core source/model.rs（local/https/git）、role.rs（明确上游/仅本地/候选）、repo.rs（UpstreamOrigin坐标）、DiscoveryFacade（网络搜索/仓库发现）和 SourceRelinkPanel/SourceUpdatePanel。
- 当前缺口：SourceRepository::relink 以通用descriptor关联并替换skill_sources；upstream_for_skill 依赖branch/directory，不完整就无上游，且按source id排序取首条，未体现用户选定更新来源。record_upstream 的source身份及坐标更新策略需核查同仓多Skill不同子目录，不能让一次关联改变其他主体的更新位置。
- 已确认增量要求：导入存证与选定上游明确分离；上游坐标按实际主体/技能路径身份持久化；复用搜索、获取、版本及生成契约流程，不能只改输入框标题而保留网址写入假成功。
- 后续TDD需覆盖候选不自动绑、同名不同主体、仓库根/子目录、同仓多技能互不覆盖、内容相同/不同、坐标不全、网络/凭据/能力受限、取消/重试、更换/解除不改导入存证或主体/链接、预览变化失效、检查/采用同源与跨页刷新。此处尚无实施/通过结果。

### 6.4 自动化与AI辅助（已确认方向与负责人执行规则）

- 点击“查找更新来源”即启动有界查找，预填原运行时名称，优先解析已有明确网络线索，复用在线搜索与登记仓库发现；提供可修改关键词和粘贴地址的补充入口，不要求用户先填仓库、分支和子目录。查询与发送范围可见，遵循既有联网和AI能力开关，不发送原始正文、脚本、个人本机路径或凭据。
- 已启用且可用的AI搜索辅助自动沿用，不要求每次重新勾选或配置；未配置/禁用/失败时普通搜索仍可用，以紧凑说明和模型设置入口表达实际情况，不阻断查找、不静默开启禁用的能力。AI可扩展检索词；首期复用现有关键词扩展能力，不新增独立AI爬虫、任意命令执行或未经确认的评分服务。
- 候选必须来自真实搜索/仓库结果或用户给定地址。自动解析精确技能目录、核验边界/包结构、比较内容并检查是否具备更新能力；使用确定性事实排序和推荐，AI不能编造URL、作者、官方身份或“已验证”结论。并发/数量/超时受限，取消后不提交关联，不无限遍历网络仓库。
- 能唯一定位的目录自动填入预览，不再让用户逐层选目录；多个同名/相似候选时明确区别。可预选一个有事实依据的推荐项，但写入仍由最后一次“关联为更新来源”确认。名称相同或只有一个搜索结果不足以确认主体身份；内容不同也不自动等于错误来源。
- 自动步骤在同一有界结果面板内显示进度、真实匹配依据及受限原因，完成后可直接确认，避免每一步单独点击“下一步”。主页面/抽屉内容区尺寸保持稳定，深层选择在浮层内进行；必要的不同来源选择不能省略为错误的自动绑定。
- 关联成功后可自动进行只读更新检查并同步显示结果，避免再点一次检查；此检查失败不伪装为关联失败或撤销已成功的来源保存，提供重试。没有采用内容的授权时不自动升级主体或修改使用链接，采用新版仍走独立影响确认/检查/备份流程。此规则不改变“全部使用链接跟随集中库当前版本”。

组合成员动作属于组织操作，不套使用关系的集中管理状态；网络更新来源及版本属于Skill生命周期，来源事实可在图谱展示但不进下游治理待办。已确认的复用修改仍是独立上游事实：由创建新主体流程落账，治理/图谱只读追溯展示已完成/复用修改，不套目标接管/修复/回收动作，不撤销其原/新删除独立边界。

### 15.1 入口与流程归属

- 同一治理动作可从关系治理、Skill详情的具体关系、Agent/项目具体关系或图谱选中边进入；都选择同一真实关系，调用相同预览/确认/执行/恢复并刷新共同事实。Skill页能有快捷入口，但不得另实现“技能级接管/修复”状态机。
- 派发是用户从Skill发起的使用关系创建流程，不是治理一条尚不存在的关系。实际创建成功才新建关系；同名占用属于派发预览的冲突，不让已正常关系变待处理、不产生虚构关系。发现已有真实待接管/异常关系时精确进入其治理步骤，不另建重复入口事实。
- 回收处理具体已存在使用关系，选全部去向只是该Skill真实关系的批集合；主体不删除。结束关系只改变指定关系/历史事实，当前位置独立文件保留。删除Skill是主体动作，由删除预览自动汇总并调用统一关系回收/结束，不列为关系治理主动作，不能要求用户逐条先回收。
- 升级/回滚操作主体当前版本，所有受管链接使用当前版本；版本变化不自动结束/重建正常使用关系。执行若发现真实链接异常，由该关系事实进入治理；升级失败或中断仍归操作/恢复模块。
- 编辑创建新主体是主体流程；复用修改由其真实创建结果记录。替换继承是这个流程内调用已有关系替换并汇总影响的选项，不新建“继承中/待继承”关系类型。不继承保留原关系并仅新增主体/复用事实。

### 15.2 单项、批量与展示

Skill列表多选形成主体集合，用于各主体实际版本检查、画像、试用、组合/导出和删除等动作；每项参数/检查/确认边界仍按各动作。关系列表/详情多选形成目标关系集合，用于接管、保留、修复、回收/结束；同一个Skill可以在一个目标正常、另一个目标异常，不能统一写成主体异常或主体已接管。

Skill列表若提供“管理所选技能的使用去向”，只是按主体集合筛出真实关系并打开治理流程；批量“回收所选技能”若后续确认提供，则同样先选实际关系范围，调用关系批流，不新增Skill回收契约或默认影响所有目标。显示可聚合使用数/待处理数，但它们是关系摘要，不与主体试用、安全结果、来源更新混成一个状态字段。

例如同一Skill处于试用、基础检查通过，同时Agent A已集中管理且正常、项目B使用链接异常：试用和检查由主体模型表达；A已完成、B待处理由关系模型表达。修复B不结束试用、不重写检查；转常规不修复B；删除主体才汇总A/B的真实删除影响。

该分类应同步关系产品裁决/统一实施计划及当前开发文档。A/B沿原授权范围共享事实和执行器，不据本轮边界说明新增通用流程引擎、页面重构或尚未确认批量入口。

## 17. 来源更新、采用版本与回滚（本轮细节讨论稿）

第7.2/15节已确认主体操作归属、旧版本保留、来源保持与受管链接跟当前版本；本节补齐执行与用户决定，新增通道默认/保持当前决定仍作为讨论项，不临时扩正在实施的R2/FB-013。

| 动作 | 主体及使用影响 | 结果与闭环 |
| --- | --- | --- |
| 检查更新 | 只读检查所选网络更新来源的精确Skill目录/通道，不改当前内容或任何目标 | 展示当前与候选的可读版本/时间及实际内容是否不同；不可达/无来源/未核验不假称最新版。无内容变化不造重复版本 |
| 采用来源新版 | 采用本次核验的候选，当前内容保留为历史版本；原主体身份/画像/试用和原更新来源保持 | 完整影响预览并经过真实基础检查，确认后切换当前内容；全部受管链接使用当前版本且一致核验，未接管独立副本不改写 |
| 保持当前版本（处理本次更新的建议） | 不改内容/目标/来源，只明确本次候选不采用 | 检查事实仍显示该候选可用，决定另记该来源/通道/候选依据；可结束该次复核提醒，之后新候选重新提醒，不把保留决定记成已最新或永久关闭更新。取消/关窗口不冒充已作决定 |
| 回滚到历史版本 | 明确选择该Skill真实完整历史版本并作为当前版本，回滚前内容继续保留 | 展示同主体受管目标全影响，目标版本真实基础检查对应内容；检查缺失/需重查时实际运行，已有相同版本记录可如实引用但不称新运行。成功后版本/文件/使用事实一致；无可用历史不提供可执行回滚 |
| 版本命名／查看变化 | 编辑可读版本备注名或只读比较现有完整版本 | 不改正文/当前选择/来源/链接；用户可读名称/来源标记/时间用于区分，不能回退展示原始VersionId/hash |

检查到有更新不自动采用，全部受管链接跟随集中库当前版本也不等于远端自动升级。采用新版和回滚均由主体流程汇总全部去向确认；不在同一次版本采用中勾选只更新部分受管链接，也不新增固定版本派发。共享目录一次物理核验，完整列消费者。未接管独立副本保持原内容，预览明确它们不会同步。实际使用异常由统一关系事实表达，正常关系不因为版本切换结束/重建。

### 17.1 本地修改与网络更新

采用网络候选将替换当前主体内容，当前本地编辑先保留为历史版本；预览用高亮说明影响，用户可采用或保持当前，不要求先走手工差异合并流程。本地编辑是否存在须有基准证据，没有证据只说明实际内容将替换，不能虚构本地冲突/无改动。继续使用已有安全门禁，FB-003警告分级未裁决；AI不能替代基础检查或自动决定内容。

不在来源更新流程新增“独立分支”主体类型/状态；用户想在原技能基础上另建，统一走编辑保存→创建新Skill（复用修改/两种继承），不以现有未实现的create_independent_branch入口声明另一种创建成功。更换/解除网络来源另属既有来源动作，不因保持当前/回滚而自动解除；复用修改创建依据不改变。

若新内容改变实际运行时名称，必须核查所有目标入口名称与SKILL声明一致及同名占用；无安全迁移能力先说明受限，不静默改源声明、显示别名或用库目录后缀解决。这里只明确约束，不额外开发真实名称编辑功能。

### 17.2 更新通道默认（作为推荐设置，不作为正常流程必答）

用户反馈操作/确认过多，第18节简化方案替代此前需要单独回答的通道问题：正常用户无需先决定发布/分支，系统沿已明确的来源设置；新来源给出实际可用且能定位本Skill的正式发布优先、否则仓库分支的推荐，在来源摘要说明并允许更多设置调整。该推荐不替代来源身份的明确确认，不更改已有明确选定分支。之前偏好问题不作为阻塞或必答，若用户另有明确偏好仍沿用；代码尚未实施新默认策略。

某仓库的正式发布必须实际包含所绑定的Skill目录且可核验，不能只取仓库标签冒充单Skill更新。选定后来源/通道固定；暂时网络失败、凭据受限、目录缺失不静默切换内容来源，重试/更换明确说明。预发布/开发内容只有真实适配器能够区分且明确选定时才采用；不承诺所有平台/下载地址都有发布能力。

### 17.3 共用采用边界与批量

更新候选与历史目标都锁定预览的实际内容/当前基线/来源坐标及关系影响集合，提交再核验。旧预览后候选、当前内容、来源或目标事实变化时重新预览，不能检查一次又下载另一版直接采用。使用一次影响确认，不另要求逐个去向确认；关系安全执行/恢复共用已批准基础，不新建更新专属治理状态机。

失败须核查当前指针、主体实际文件、portable/数据库与受管目标是否一致；安全回退保留原内容/关系，未确认恢复的中断进恢复中心，不能仅恢复指针或吞恢复异常后报成功。旧安全结果不冒充新内容检查；检查结论、运行失败和用户保持决定分别呈现。结果同步列表/详情/检查/来源/图谱及待办，不依赖通知点击。

批量检查更新沿实际Skill集合逐项只读；批量采用需每个Skill精确候选和影响，可聚合同类确认但逐项真实结果/受限/恢复。回滚没有通用“全体上一版”，每个Skill必须明确可用目标版本；未提供对应契约不展示批量成功按钮。不提供批量编辑正文或混合动作的一键自动采用。

## 18. 减少用户选择与确认（用户已确认）

用户指出第17节对用户可能过于复杂、确认过多，随后回复“可以，还有么”，确认一次意图一次必要影响确认、轻量保存不二次确认的简化方向。内部规则用于开发与核验，不应逐条成为选择框/独立步骤。正常路径由系统合并准备和执行，用户只决定有实际影响的结果；模型职责分层不要求用户在页面之间手工衔接。以下为已确认交互规则，不宣称现有代码已实现。

| 用户意图 | 系统自动完成 | 正常路径的写入确认 |
| --- | --- | --- |
| 查看／检查更新／基础重新检查 | 查询、实际检查、明确状态/时间及结果同步；沿既有网络/数据/能力授权 | 不增加确认。AI检查沿已允许配置/范围，范围变化另明示，不静默新授权 |

### 18.1 更新的常用入口

- 用户入口以“更新”及版本历史中的“恢复此版本”为主；“检查更新”是可选只读刷新，无须先手动检查再跑完整流程。系统在既有授权范围准备，不静默开启网络/AI或扩大发送数据。
- 正常更新面板简洁说明“当前→新版、将同步哪些受管使用目标、当前版本会保留可恢复”；显示独立副本不自动更新及真实限制的摘要。完整目标列表/来源通道/文件变化收在有界展开区，关键本地修改替换、共享全影响及实际风险直接高亮可见，不仅tooltip。
- 下载、基础检查、核验和影响查询呈现系统进度，不作为用户必须逐条点击下一步的页面。AI辅助可用时沿现有许可自动辅助检索；用户不需要每次重新选择模型。实际写入由最后明确更新决定授权。
- 已知来源使用已明确设置，新来源的通道由系统给出可核验推荐，更多设置可改；不让普通用户必须理解branch/tag/版本ID。源身份不充分或多候选真实有歧义时仍需选来源，不能用简化当作同名自动绑定。
- 没有来源而用户发起更新，可在同一有界流程内自动查找/核验、选定真实来源及准备新版，最后一次确认明确“关联此来源并更新”的组合影响；只想登记来源时可选择“只关联”。两种职责仍分别落账；失败如只成功关联必须明确反馈并安全处理，不称更新成功。无需先完成两个页面和两次同样更新影响确认。
- “保持当前”不再要求每次检查后必须作答，关闭/取消本来就保留当前且不写决定；“忽略本次更新”若提供，收在次要操作、只作用于该候选，按第17节决定/观察分离，不新增永久免更开关。不是把取消自动当治理/复核已完成。

### 18.2 合并确认的边界

一次确认针对同一明确意图、同一实际范围和版本；预检/提交再核验仍完整。没有改变用户可见影响的技术重试可自动完成，取消不可逆步骤前生效；实际内容/所有权/影响范围变化、同名占用、未知/受保护对象或真实高风险需要明确新选择/更新预览，不能无限循环确认或暗选危险答案。

批量同类动作在一个汇总面板列可执行/受限范围、共享影响及按项版本/内容决定，确认一次后逐项执行/结果/恢复；存在真正不同的内容选择时按组在同一面板指定，不合成无意义的一键全部采用。单项和批量的危险动作不能为追求一次确认隐藏重要事实；不同意图的主体删除与普通导出不会被自动捆绑。

后续入口设计不把整个动作目录铺成固定按钮，列表/看板/抽屉内容区稳定。用户明确要求先整体梳理每个操作的入口位置，再决定主动作/透明编辑/有界更多操作等呈现方式；不能提前把所有非主操作收进“更多”。该规则加入AGENTS与统一计划，当前R2/FB-013继续原实现范围，不临时重写所有页面或绕现有门禁。

### 18.3 后续可进一步简化的入口建议（讨论项）

- 按当前真实状态突出推荐动作，例如有新版时“更新”、入口异常时“修复”、未集中管理时“转为集中管理”。用户认可简化方向，但“其余可执行动作放更多”尚未定稿，先按第18.4节梳理入口，再逐项决定呈现。多个事实并存仍分别说明，推荐不是新状态或自动代用户决定。
- 自动汇总所有真实受管去向，不要求用户在版本更新时重复选择目标；派发仍需要真实目标选择。记住安全的显示/筛选偏好，不记住危险覆盖确认、不把上次权限当新范围授权。
- 成功用简短结果及即时刷新反馈，不再弹“确定”才能结束。批量结果先呈现成功/未完成数量及真实下一步，详情有界收纳；通知不是刷新开关。
