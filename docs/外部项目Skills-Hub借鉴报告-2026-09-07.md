## P0：跨设备 Skill 库同步

### 借鉴点

参考项目把一台机器上的集中库通过私有 Git（版本控制）仓库与其他设备同步。它的价值不在“能推送”，而在于同步过程中把高风险状态显式建模：设备、变更预览、冲突、历史、回收站和调度状态均可查询。

参考实现证据：

- `src/components/skills/DeviceSyncPage.tsx` 同时加载配置、状态、历史、冲突、回收站、OAuth（授权）能力和设备清单（第 96–218 行）。
- `src/components/skills/deviceSyncState.ts` 将体验状态限定为“未连接、健康、有变更、失败、冲突、同步中”，并根据配置、冲突数、运行状态和上次结果决定当前界面（第 115–218 行）。
- `src-tauri/src/core/device_sync/text_merge.rs` 对不大于 1 MiB 的 UTF-8（统一码转换格式）文本做三方合并；二进制、大文件、混合换行或冲突一律转人工处理，而非强行覆盖（第 5–82 行）。
- `src-tauri/src/core/device_sync/scheduler.rs` 支持固定间隔或每日定时，并在失败后退避、在未解决冲突时暂停（第 1–220 行）。

### 应在当前项目实现的产品边界

同步对象仅限于“集中库中可移植的 Skill 内容与其元数据”，**不**同步本机绝对路径、系统凭据、运行日志、缓存、安装包和设备专属部署记录。每台设备在拉取后根据本机 Agent（智能体）目录重新生成部署计划。

建议分两个版本交付：

1. **V1：手动、安全、可恢复。** 连接一个私有 Git 仓库；执行“检查变更 → 预览 → 同步”；发生同文件双边修改时生成冲突，不自动覆盖。
2. **V2：自动化。** 在 V1 的审计记录和冲突模型稳定后，才增加定时检查、定时同步与失败退避。公共仓库上传始终要求单次明确确认，默认只允许私有仓库。

### 建议领域模型

在 `skillhub-core` 新增不依赖 Tauri 的同步子域，至少包含：

| 概念 | 关键字段 | 目的 |
| --- | --- | --- |
| `SyncConfig` | 仓库定位、分支、同步模式、调度、最后成功提交 | 保存非敏感配置 |
| `SyncManifest` | Skill ID、可移植相对路径、内容哈希、基线提交 | 判断增删改并提供三方合并共同祖先 |
| `SyncDevice` | 随机设备 ID、别名、最近提交、最近活动时间 | 显示“待同步/已同步/过期”，不是在线状态 |
| `SyncChange` | 新增、修改、删除、冲突、影响 Skill | 让用户先看计划再执行 |
| `SyncConflict` | 路径、基线/本地/远端快照、可选决策 | 支持保留本地、保留远端、手动合并 |
| `SyncRun` | 开始/结束时间、阶段、错误码、提交、结果摘要 | 提供可审计历史和可操作错误 |
| `SyncTrashEntry` | 删除前快照、到期时间、恢复状态 | 与当前项目的数据保护能力衔接 |

其中 `SyncManifest` 必须使用当前项目已有的稳定 Skill/版本标识和内容哈希，不以显示名称匹配；否则重命名会被误判为删除加新增。

### 同步算法（应借鉴，不能直接搬代码）

```text
锁定同步任务
  → 读取并校验远端清单
  → 与本地基线清单比较，生成预览
  → 无冲突：合并到暂存目录并校验哈希
  → 原子替换集中库；记录 SyncRun；推送新清单
  → 有冲突：保存 SyncConflict；不改集中库；界面转“需处理”
```

具体规则：

- 只对有共同基线、UTF-8 且不超过 1 MiB 的文本尝试三方合并；合并结果仍要过哈希和路径边界校验。
- 二进制文件、超过上限的文件、符号链接语义冲突、删除与编辑并发、或任何未验证快照，全部进入人工冲突，不推测用户意图。
- 提交前写入暂存目录，校验完成后再原子替换；失败时保留原集中库和诊断信息。
- 删除先进入应用回收站并设保留期；当前项目已有备份、恢复和卸载影响评估，应复用这些能力而不是维护第二套不可恢复删除。
- 凭据只保存到现有系统凭据适配器；数据库仅保存凭据引用。同步线程只在任务实际执行时读取凭据。
- 同步前后通过当前部署服务做“重新核对”，但不要把某台电脑的部署路径、链接方式或外部修改同步给其他电脑。

### 前端设计规格

新增一级页面“设备同步”，采用两态页面而非堆砌表单：

| 状态 | 页面主体 | 主操作 | 必须呈现的信息 |
| --- | --- | --- | --- |
| 未连接 | 三步向导：授权 → 选择/创建私有仓库 → 首次同步 | 连接并首次同步 | 数据范围、私有仓库说明、公共上传二次确认 |
| 健康 | 状态卡 + 设备/历史/冲突/回收站四个标签页 | 检查变更、立即同步 | 最近成功时间、下次计划、其他设备的“待同步”数量 |
| 有变更 | 变更摘要卡 | 查看预览、同步 | 新增/修改/删除分别计数，受影响 Skill 列表 |
| 冲突 | 冲突置顶、默认打开冲突标签页 | 逐项决策 | 基线/本地/远端差异，明确“不会自动覆盖” |
| 失败 | 错误卡与最近运行记录 | 重试、查看详情 | 稳定错误码、阶段、恢复建议，不能只显示原始异常 |

参考项目的可借鉴细节是：将仓库加载区分为超时、凭据错误和一般失败；仓库列表仅展示私有仓库；切换仓库会重置可见性确认；状态机有确定优先级（同步中 > 冲突 > 失败 > 有变更 > 健康）。这些能显著减少用户在同步风险上的误判。

### 当前项目的接入位置

- `crates/skillhub-core`：同步领域模型、清单差异、冲突决策及端口（port，抽象接口）。
- `crates/skillhub-application`：同步用例编排、预览/执行两阶段、操作记录。
- `crates/skillhub-adapters`：Git、系统凭据、调度和文件暂存的具体适配器；复用现有路径校验、链接处理和内容扫描原则。
- `crates/skillhub-storage`：同步配置、设备、运行记录、冲突和回收站持久化。
- `apps/desktop/src/features`：新增独立 `device-sync` 功能目录；通过现有绑定生成流程暴露契约，不能手写重复 TypeScript（TypeScript）接口。

### 必须先写的测试

1. 同一文件的非重叠文本修改可自动合并，重叠编辑必须生成冲突。
2. 二进制、超限文件、混合换行、哈希不匹配均不得自动合并。
3. 拉取/合并/推送任一步失败不会修改集中库；原子替换失败可恢复。
4. 远端删除与本地修改、同名不同 ID、重命名、路径穿越、符号链接均有确定结果。
5. 公共仓库、未知可见性、凭据缺失、仓库切换、并发同步、网络失败退避、冲突暂停调度均覆盖。
6. 同步后的本机部署重新核对不覆盖独立的工具端改动，且不把本机绝对路径写入远端。

## P1：精选优先的在线 Skill 发现

### 借鉴点

当前项目已有在线搜索和受控导入；参考项目的增量优势在于把“精选目录”和“关键词搜索”放进同一浏览体验：无搜索时先呈现精选项；输入关键词后同时显示命中的精选项与去重后的网络结果；每张卡展示来源、摘要、星标/安装量，并明确已安装状态。

其后端还把精选清单设计成“远端更新 → 本地缓存 → 内置兜底”的三级来源：远端加载失败时仍返回缓存或随应用发布的静态列表，而不是使发现页不可用。参考依据为 `src-tauri/src/core/featured_skills.rs` 第 7–13、44–103 行；前端分层与已安装去重在 `src/components/skills/ExplorePage.tsx` 第 58–76、118–218 行。

### 推荐实现

在当前“在线发现”模块内增加“推荐”区，而不是新增平行入口：

1. 发布一份仓库内、可审查的 `featured-skills.json`，字段仅含名称、简介、来源 URL、分类、维护日期和展示排序；不要将其等同于安全背书。
2. 启动或打开页面时按“签名/校验过的远端清单 → 上次验证缓存 → 内置清单”读取；界面显式标明来源与最后更新时间。
3. 搜索结果分为“推荐匹配”和“在线结果”，按规范化的 `来源 + Skill 标识` 去重，已在库中的项显示“已导入”并可跳转详情。
4. 用户点击安装仍必须进入现有导入、扫描、安全检查和冲突决策流程；推荐卡绝不绕过当前项目的安全边界。

### 前端细节

- 复用当前发现页的独立子页与导入向导；顶部使用一个搜索框，下面先显示推荐网格，再显示在线结果网格。
- 卡片只承担“识别、可信线索、安装入口”三件事：名称、两行摘要、来源、分类、维护度/热度和安装状态。不要在卡片内塞入部署目标或安全检查结果。
- 搜索为空时保留推荐内容；搜索中使用骨架或明确加载状态；网络不可用时保留已验证的推荐清单并显示轻量提示。
- 参考项目 `docs/assets/explore-online-skills.png` 的双区卡片布局和卡片右上角即时安装状态可直接作为视觉参考；颜色、字体、组件仍应沿用当前项目设计系统。

### 验收条件

- 断网、远端 5xx（服务器错误）、无缓存三种场景均有不同且准确的状态。
- 精选与搜索结果去重；已导入 Skill 不显示可重复安装操作。
- 任何推荐项安装均完整经过当前导入安全检查；伪造 URL、重定向和非受支持来源仍被拒绝。
- 清单升级、缓存过期、字段缺失和本地化文案都有测试。

## P1：可配置扫描来源与待导入提醒

### 借鉴点

参考项目把“扫描哪些目录以发现可导入 Skill”和“向哪些工具部署 Skill”明确分为两套配置。用户可逐个开关扫描来源，保存后重新扫描；主列表在发现候选时给出醒目的“发现待导入”横幅，并提供“调整扫描范围”和“审查并导入”两个并列操作。

参考依据：`src/components/skills/modals/DiscoveryScanModal.tsx` 第 26–123 行实现可访问的逐项开关、已启用计数及“保存并重新扫描”；`src/components/skills/SkillsList.tsx` 第 85–117 行实现待导入横幅。该模式对拥有多个 Agent（智能体）和自定义目录的用户尤其有价值。

### 推荐实现

- 在当前发现模块增加持久化的 `DiscoverySource` 配置：唯一键、显示名、经过脱敏的路径提示、来源类型、启用状态和上次扫描结果。
- 部署目标继续保持独立；关闭扫描某个 Agent 目录不能停用该 Agent 的部署，也不能删除已导入内容。
- 扫描结果只收集包含 `SKILL.md` 的有效目录，并沿用当前扫描器的真实目录、符号链接和边界校验规则。
- 在库页顶部仅当存在新候选时显示横幅；横幅不直接导入，而是进入当前候选选择与冲突处理工作流。

### 前端细节

- 设置弹窗按“来源名称 + 路径 + 开关”单行排列，顶部显示“已启用 X/Y”，底部主按钮为“保存并重新扫描”。
- 待导入横幅应使用与普通信息通知不同的强调色；右侧保持两个动作：次级“扫描设置”、主操作“审查候选”。
- 重新扫描期间禁用重复提交，完成后将焦点和结果摘要返回横幅，满足键盘与读屏器（screen reader）可用性。

### 验收条件

- 配置跨重启保存；关闭来源后不扫描也不删除历史候选的审计记录。
- 用户设置、默认来源和自定义目录重复时按规范化真实路径去重。
- 扫描结果有来源归属；候选目录失效、无读取权限和软链接越界都能显示可操作错误。

## 实施顺序与取舍

1. 先完成 P0 的领域模型、清单/预览/冲突测试和手动同步；在没有原子写入、回收与冲突闭环前，不暴露“自动同步”。
2. 再交付 P0 的设备同步页面和操作历史，接入当前数据保护、操作记录和部署核对。
3. P1 的精选目录可独立并行实施，改动集中在发现读模型与现有在线发现页。
4. 扫描来源控制在 P1 中随本地发现工作台落地；它不依赖跨设备同步。

不建议复制参考项目的单体页面状态、手写 Tauri DTO（数据传输对象）或其硬编码工具目录表。当前项目已有更适合长期维护的分层、绑定生成、路径安全和导入检查机制；借鉴应保持在上述能力和交互契约层。
